# 0506 WebRenderBench Generate 数据续构造任务理解与执行计划

## 目标

基于 `CA877/WebCodingSft` 原有 `data_pipeline` 策略，并结合后续确认的 WebRenderBench 全项目渲染方案，继续构造三类 generate 任务：

| 任务类型 | 目标数量 | 构造方式 | 主要输入 |
|---|---:|---|---|
| text-based generation | 10,000 | Playwright 截取完整项目全部页面，再由可读图模型逆向生成 WebCompass 风格 PRD | full-page screenshots |
| vision-based generation | 10,000 | Playwright 截取完整项目全部页面，不转文字 | rendered screenshots |
| video-based generation | 10,000 | Playwright 对每个页面滚动录屏，覆盖完整页面 | recorded videos |

核心原则：先检查已有 `data_pipeline/output/generate` 结果质量，再在云数据盘上的 WebRenderBench 数据基础上断点续跑扩量。

本轮明确前提：generate SFT 数据不需要 `checklist` / `problem_statement`。只要三类任务各自满足 WebCompass generation 输入格式即可。

## GitHub 当前策略

核心入口是：

- `data_pipeline/batch_generate.py`
- `data_pipeline/image_reverse.py`
- `data_pipeline/video_generate.py`
- `data_pipeline/common.py`

整体思路是 reverse construction：

```text
真实网页资源
  -> 读取源码 / 渲染截图 / 录制交互视频
  -> LLM 反推网页设计文档或视觉描述
  -> 写入 WebCompass 风格 JSONL
  -> 用 manifest 支持断点续跑
```

当前 `batch_generate.py` 支持：

```bash
python -m data_pipeline.batch_generate \
  --page_dirs /path/to/pages \
  --output_dir data_pipeline/output/generate \
  --task text \
  --mode code \
  --limit 0
```

关键输出约定：

- `data_pipeline/output/generate/text_generation.jsonl`
- `data_pipeline/output/generate/image_generation.jsonl`
- `data_pipeline/output/generate/video_generation.jsonl`
- `data_pipeline/output/generate/manifest_text.jsonl`
- `data_pipeline/output/generate/manifest_image.jsonl`
- `data_pipeline/output/generate/manifest_video.jsonl`
- `data_pipeline/output/generate/screenshots/<instance_id>/...`

## 云数据盘使用计划

用户提供的 WebRenderBench 数据在云数据盘机器上。连接信息只从本机 `.env` 或运行时环境变量读取，不写入仓库：

```bash
ssh -p "$SEETACLOUD_PORT" "$SEETACLOUD_USER@$SEETACLOUD_HOST"
```

后续操作时不把密码写入脚本。登录后先只做只读盘点：

```bash
pwd
ls -lah
find / -maxdepth 4 -iname '*webrender*' 2>/dev/null | head
find / -maxdepth 5 -type d \( -name 'train_webpages' -o -name 'test_webpages' \) 2>/dev/null
```

确认 WebRenderBench 页面目录后，再建立本地/远端工作路径，例如：

```bash
export WRB_ROOT=/path/to/WebRenderBench
export PAGES_DIR="$WRB_ROOT/train_webpages"
export OUT_DIR=/path/to/WebCodingSft/data_pipeline/output/generate
```

## 质量检查清单

在扩量前，先跑已有结果检查：

1. JSONL 结构检查：每行可解析、字段齐全、`instance_id` 唯一。
2. instruction 内容检查：长度下限、三段式标题完整、不包含“source code / screenshot / frame”等泄露逆向来源的措辞。
3. 来源页面检查：每个 `instance_id` 能映射回原始网页目录，且覆盖 WebRenderBench 的 train/test 两个 split。
4. 截图检查：vision/video 任务必须有可打开的截图或帧图，且不是空白页。
5. manifest 检查：manifest 与 JSONL 对齐，失败/skip 不能被误算进每类 10k。
6. 抽样人工检查：每 500 或 1000 条抽样 20 条，看描述是否具体、可执行、不过度照抄代码。

## 数量判断

当前数量远远不够。

截至 2026-05-06 从 Hugging Face 页面确认，WebRenderBench `default` 子集共约 45.1k rows，包含两个 split：

| split | 数量 |
|---|---:|
| train | 约 22.6k |
| test | 约 22.5k |
| total | 约 45.1k |

用户目标是三类任务各 10k，总计 30k 条 generate 数据。当前 GitHub 可见结果只有 16 条 text，image/video 为 0，因此不能直接满足目标。

由于 WebRenderBench train + test 总量约 45.1k，理论上足够支撑 30k 任务。后续不应只使用其中一个 split，而应把 `train_webpages` 和 `test_webpages` 合并成候选池，再按 text/image/video 分别取够 10k。建议每条 WebRenderBench 页面只生成一种主任务，避免三类数据高度重复；如果希望每个页面生成多模态变体，也需要在 `instance_id` 中加 `text_` / `image_` / `video_` 前缀防止冲突。

## 扩量策略

先小批量验证，再逐级扩大：

```bash
# text 小批量；PAGES_DIR 应包含 train/test 合并后的页面候选
python -m data_pipeline.batch_generate \
  --page_dirs "$PAGES_DIR" \
  --output_dir "$OUT_DIR" \
  --task text \
  --mode code \
  --limit 50

# vision 小批量
python -m data_pipeline.batch_generate \
  --page_dirs "$PAGES_DIR" \
  --output_dir "$OUT_DIR" \
  --task image \
  --mode vision \
  --limit 50

# video 小批量
python -m data_pipeline.batch_generate \
  --page_dirs "$PAGES_DIR" \
  --output_dir "$OUT_DIR" \
  --task video \
  --mode code \
  --limit 50
```

小批量通过后，再分别补到 10k：

```bash
python -m data_pipeline.batch_generate --page_dirs "$PAGES_DIR" --output_dir "$OUT_DIR" --task text  --mode code   --limit 0
python -m data_pipeline.batch_generate --page_dirs "$PAGES_DIR" --output_dir "$OUT_DIR" --task image --mode vision --limit 0
python -m data_pipeline.batch_generate --page_dirs "$PAGES_DIR" --output_dir "$OUT_DIR" --task video --mode code   --limit 0
```

text-based 构造使用可读图的多模态模型，从完整页面截图生成 PRD。DeepSeek 这类文本模型不能直接承担截图理解步骤，只能用于不需要读图的辅助整理或校验。

API key 配置只放环境变量：

```bash
export OPENAI_BASE_URL="https://api.deepseek.com"
export OPENAI_API_KEY="$DEEPSEEK_API_KEY"
```

必要时修改 `data_pipeline/common.py` 中的模型名，或做成命令行参数，避免每次手改代码：

```python
TEXT_MODEL = "deepseek-chat"
```

## 需要补强的代码点

为了稳定产 3 x 10k，建议先补以下能力：

1. 给 `batch_generate.py` 增加 `--target-count`，按有效 JSONL 行数补齐到目标数量，而不是只按本轮 `limit` 跑。
2. 给 `--start-after` 或 `--shuffle --seed`，避免每次都从同一批页面开头扫。
3. 给 text/image/video 三类都统一质量校验函数，失败样本写 `manifest` 但不写入主 JSONL。
4. 修正当前日志里 `problem_statement` 长度打印不准确的问题。
5. 增加 `validate_generate_jsonl.py`，输出每类数量、重复 ID、字段缺失、instruction 章节完整率、截图/帧缺失率。
