## 1. 任务定义、schema 与项目主线未完全收口

### 问题
- 七类任务已经形成，但最终统一 schema 一度没有冻结，generation、editing、repair 的字段和落盘形式存在返工风险。
- `sp/mp` 容易被误解为新任务大类，实际只是 editing/repair 的 split 或样本属性。
- text/image editing、text/image repair 如果各自独立构造，会导致底层样本重复、流程膨胀。
- video-editing、video-repair 等扩展想法会让当前阶段复杂度失控。
- 主线数据构造和后续增强想法混在一起：视觉差异诊断、特效、自我诊断、找不同等都很有价值，但不是第一阶段的阻塞点。

### 解决方案
- 先冻结七类任务：`text-generation`、`image-generation`、`video-generation`、`text-editing`、`image-editing`、`text-repair`、`image-repair`。
- 明确 video 只属于 generation，暂不扩展 video-editing/video-repair。
- 明确 `sp/mp` 只作为 editing/repair 的属性，不和七类任务并列。
- 让 text-editing 与 image-editing 共用同一批 `src -> dst` pair；text-repair 与 image-repair 共用同一批 `broken -> clean` pair。
- 底层真实要构造的 pair 收敛为 5 种：text-generation、image-generation、video-generation、editing pair、repair pair。
- 冻结每类样本字段后再大规模跑数：generation 包含 `instruction`/视觉输入、代码、资源、meta；editing/repair 包含 `description`、`src_code`、`dst_code`、`label_modified_files`、资源和可选截图。
- 把高级 repair/self-critique/difference modeling 放到第二阶段增强方向，不阻塞主线。

## 2. 规模化产线尚未完全跑通

### 问题
- generation 是最接近量产的部分，但正式 30K/三类 10K 产物尚未稳定跑出。
- text/image/video generation 规划清楚，但需要先从小规模 smoke test 逐步放大。
- editing/repair 有 prototype 和 prompt/search-replace 思路，但缺少统一批量入口。
- 当前整体目标是 7 类任务 × 10K = 70K；预处理要覆盖 WebRenderBench 31,765 项目和 WebCode2M URL，但服务器批量执行、CSS 拆分、统一合并到构造阶段仍是未完成项。

### 解决方案
- 优先顺序：冻结 schema → 修复并跑通 generation v2/v3 → 把 edit/repair 合成统一入口 → 再做视觉差异/特效/自诊断增强。
- generation 放大节奏：先 20 条，再 1K，再 10K。
- edit/repair 放大节奏：先统一 `src_code / dst_code / label_modified_files / resources / screenshots` 字段，跑 20 条小规模样本，抽检后再扩大。
- 通过 `construct_webcode2m_dataset.py` 统一调度七类任务。
- Phase 1 先预处理得到离线可渲染项目；Phase 1.5 拆 CSS；Phase 2 构造任务；Phase 3 用验证脚本检查。

## 3. Pipeline A/B 运行失败、污染与断点问题

### 问题
- generation v2/远端正式跑曾被 Playwright/Node `write EPIPE` 打断。
- Pipeline B 首次启动时并发过高（30→80），Chromium 大量 EPIPE 崩溃，导致前 224 条 URL 被错误标记为 `site_timeout`/`empty_page`。
- 前 224 条污染样本已经写入 manifest，续跑时会被跳过，导致实际产出率只有约 2.2%，低于正常预期约 40%。
- add_js 阶段曾全部失败：`build_code_context` 返回 0 字符，`read_code_bundle` 找不到文件。
- add_js 根因判断为子进程中 `construct/construct_common.py` 的 `CODE_EXTS` 导入失败，大概率是 `__pycache__` 未清干净。
- Pipeline A 的 expand/add_js 全量策略仍需确认，尤其要在 add_js 成功后再决定是否把 expand 加回 fast 模式。

### 解决方案
- 对 EPIPE：降低并发，先做小批量 smoke test，再阶梯式放大；服务器容量下纯 clean+add_js 建议 30-50 并发，expand 模式建议 10-15 并发。
- 对 Pipeline B 前 224 条污染：当前 run 跑完后，删除这 224 条的 manifest 条目及其输出目录，然后重新处理。
- 对 add_js 失败：彻底清理 `__pycache__` 后重启 `run_pipeline_a_fast.sh`，先验证 add_js 成功率。
- 对 expand：纯 HTML expand 20s 内可完成 3 个子页面，可以加回 fast 模式，但前提是 add_js 已修好并验证通过。
- 对断点：Pipeline B 自动跳过已处理 URL；Pipeline A 如需重跑用 `--overwrite`。

## 4. 服务器资源、并发与网络代理问题

### 问题
- 服务器 17GB 内存下，130+ Chromium 会崩。
- h-liu 服务器可直连 Google/GitHub/Wikipedia，但浏览器代理兼容性不稳定。
- HTTP 代理 `httpproxy-headless.kubebrain.svc.pjlab.local:3128` 对浏览器流量兼容性一般。
- 图片下载有时必须走代理，例如 `picsum.photos` 直连会超时。
- 本地/服务器代理参数容易混淆：Chromium 不支持 `socks5h`，requests 需要远程 DNS 时应使用 `socks5h`。

### 解决方案
- 控制并发：纯 clean+add_js 用 30-50，expand 用 10-15；较保守配置可从 5/10 并发起。
- API 调用可直连时不走代理，例如 `httpx.Client(proxy=None)`。
- Playwright/Chromium 使用 `socks5://127.0.0.1:13659` 或 HTTP 代理；requests 使用 `socks5h://127.0.0.1:13659`。
- 服务器如果直连网络可用，browser/request proxy 都传空字符串。
- `playwright_crawl.py` 支持自动读取 `https_proxy` / `http_proxy` / `ALL_PROXY` 环境变量，但生产运行建议显式配置。

## 5. 网页预处理、离线渲染与资源清洗问题

### 问题
- 原始网页存在远程图片、远程 CSS、外部链接、脚本、iframe、音视频等依赖，直接用于训练会导致离线不可渲染。
- 部分页面 CDN 依赖缺失时，渲染验证会失败。
- WebCode2M URL 按字典序排列，前段集中出现数字域名、托管临时页、CDN/统计域、奇怪子域，不能直接取前 N 个估计成功率。
- 网站会出现 challenge page、停放页、默认服务器页、非 HTML 资源、空页面、错误语言等低质量样本。
- clean 与 expand 顺序如果反了，会把外链改成 `#`，导致后续无法发现导航子页面。
- 过长文件、超大页面、超多资源会拖慢 pipeline 或污染训练样本。

### 解决方案
- 所有项目预处理成离线可渲染、自包含目录：`index.html`、可选子页面、`resources/`。
- 清洗策略：下载远程图片到 `resources/`，远程 CSS 内联，外部链接中和，删除脚本/iframe/音视频，清理泄露远程 URL 的特殊属性。
- 每页资源设置上限，例如 `MAX_RESOURCES_PER_PAGE=50`，避免超大页面无限等待。
- WebCode2M 先做两层筛选：URL 形态过滤并确定性打乱，再用 HTTP preflight 剔除 challenge/parked/default/empty/non-HTML 页面。
- 顺序固定为 expand → clean，不能反过来。
- 用 `validate_webcode2m_task_dirs.py` 检查最终目录、远程 URL 残留、视频大小、字段完整性等。
- 将过长文件过滤、Playwright 渲染截图、小模型视觉质量打分归入质量控制分支。

## 6. 数据源选择、可用性与质量问题

### 问题
- `xcodemind/webcode2m` 和 `webcode2m_purified` CSS 基本自包含，但图片仍需要本地化。
- WebSight v0.2 依赖 Tailwind CDN 和 Unsplash 远程图，不是完全自包含。
- `mrm8488/WebSight_70k` 自包含但页面较短、较简单。
- SALT-NLP/Design2Code-hf 质量高、CSS 内联，但只有 484 条，规模太小。
- `bigcode/the-stack`、`Yuxiang-Luo/WebUIBench` 等数据源 gated/401，不可直接访问。
- 使用 WebRenderBench 构造 SFT 时有 WebCompass 测试集泄漏风险。
- 部分 WebCompass 任务没有 ground truth 或依赖人工/agent 生成 ground truth，数据可靠性不同。

### 解决方案
- 以 WebCode2M/WebRenderBench 作为主数据源，WebSight_70k 等作为补充。
- 对 WebSight Tailwind CDN 数据，要么下载并内联 Tailwind，要么解析 Tailwind class 成样式，要么接受外部依赖；训练主线优先选自包含程度更高的数据。
- Design2Code-hf 更适合 benchmark/validation，而不是训练主数据。
- gated 数据源暂不纳入主流程。
- 使用 WebRenderBench 前建立 WebCompass 黑名单，按网页 ID/域名去重，避免测试集泄漏。
- 对不同来源标记是否有 ground truth：逆向构造有源码答案；正向 URL 构造常只有 query/checklist；agent 生成答案需额外渲染验证。

## 7. WebCompass 本地运行与评测环境问题

### 问题
- `create_traj.sh` 同时导出 `ANTHROPIC_API_KEY` 和 `ANTHROPIC_AUTH_TOKEN`，Anthropic SDK 会同时发送 `X-Api-Key` 和 `Authorization: Bearer`，部分 API 代理拒绝。
- Claude 命令里 `--model opus` 曾硬编码，未使用 task/config 中读取到的模型名。
- Docker 默认 `cpus="16"`、`memory="64g"` 超过 macOS Docker Desktop 限制。
- Docker `--mount type=bind` 在 macOS Docker Desktop/VirtioFS 下要求目标路径预先存在，容易报 path does not exist。
- macOS VirtioFS 文件同步有延迟，容器启动时可能读不到刚创建的文件。
- 项目自带 Dockerfile 依赖内部镜像源，新电脑或外部环境难以构建。
- `anthropic_base_url` 如果包含 `/v1`，Claude Code SDK 会再拼 `/v1/messages`，变成 `/v1/v1/messages` 并触发 WAF/请求失败。
- `evaluate.py` 期望 `checklist.json` 在 `<output_dir>/<instance_id>/checklist.json`，但 Docker 实际生成在更深路径，导致 `Tasks evaluated: 0`。
- Docker 容器网络可能无法访问外部 API。

### 解决方案
- 当 `ANTHROPIC_AUTH_TOKEN` 已设置时，跳过导出 `ANTHROPIC_API_KEY`，只保留一种认证头；运行前也可 `unset ANTHROPIC_API_KEY`。
- 将 `--model opus` 改为 `--model "$MODEL_ARG"`。
- macOS 本地把 Docker 限制改为 `cpus="10"`、`memory="16g"`，并确保 Docker Desktop 分配足够资源。
- 将 bind mount 从 `--mount` 改为 `-v source:target`，让 Docker 自动创建目标目录。
- Docker 命令前加短暂 `time.sleep(2)` 等待文件同步。
- 新增 `Dockerfile.build`，使用阿里云 apt 镜像和 npmmirror npm 镜像替代内部源。
- `anthropic_base_url` 写到 `/api/anthropic`，不要包含末尾 `/v1`。
- 评测后把深层 `generated_web_pages/testbed/checklist.json` 复制到 `evaluate.py` 期望路径，或修改评测路径逻辑。
- 网络不通时检查 `network_mode`，Linux 可试 `host`，macOS 下需注意 host 行为不同。

## 9. Image/Video 数据构造与交互覆盖问题

### 问题
- image 正向构造量大但通常没有 ground truth；逆向构造有 ground truth 但依赖已有源码。
- video 任务需要体现交互、动画和时序变化，纯静态页面不适合。
- 自动录屏脚本通常只做滚动和随机点击，复杂交互覆盖有限。
- 大图或超高分辨率图片可能超过 API 限制；RGBA 图片也可能不被接口或下游处理很好支持。

### 解决方案
- image generation 同时保留两种路径：逆向构造用于 SFT（源码作答案），正向构造用于无监督/query-only 或评测补充。
- video generation 优先选择有丰富交互的网页源码，自动录屏并用 ffmpeg 提取关键帧。
- 对复杂交互网页，引入人工规划浏览路径或更智能的交互策略。
- 对超过 4MB 或 7000px 的图片自动缩放，RGBA 转 RGB。
- video 任务 query 要描述 hover/click/scroll 等状态变化，不只描述静态外观。

## 10. Edit/Repair 数据来源与统一 pipeline 问题

### 问题
- edit 可从 agent 生成中间状态、GitHub commit diff、人工/LLM 合成编辑需求中构造，但来源多，格式需要统一。
- repair 数据需要描述 bug，但不能泄露修复方案；还要处理“告诉具体问题”和“只告知有 bug”的不对称难度。
- 从 GitHub commit diff 构造 edit 时，merge commit、大重构、超小/超大 diff 都会污染样本。
- agent 生成过程如果不记录中间状态，无法自动复用为 edit/repair。

### 解决方案
- 统一 pipeline：一次 agent generate 过程同时产出 generate、edit、repair。
- 在 Docker/agent 的 CLAUDE.md 中要求 git commit：初始 commit、每个可运行功能用 `CHECKPOINT:`，每次修 bug 用 `BUGFIX:`。
- 用 `edit_from_git.py` 解析 git log：相邻 CHECKPOINT/other commit 生成 edit，BUGFIX 前一版本生成 repair。
- GitHub commit diff 筛选规则：非 merge、只改前端文件、改动文件数 <= 10、diff 大小 50-10000 字符。
- repair 描述由反向 diff 生成，只描述问题，不直接透露修复方案。
- 一条 generate query 预计可产出 4-7 条训练数据，提高数据利用率。

## 12. 成本、token 与运行节奏问题

### 问题
- WebCompass 单 case 评测阶段 token 消耗远大于推理阶段：推理约 5K tokens，Docker 内 Claude Code 验证约 2.7M tokens（含缓存读取）。
- 单 case 评测耗时约 5-10 分钟，示例为 372 秒、64 轮。
- API 成本使得 pipeline 虽已跑通，但尚未适合直接大规模无筛选生产。

### 解决方案
- 先做 1-2 条或 3-5 条端到端小规模试生产，再扩大规模。
- 便宜文本模型用于 checklist/edit 描述等文本任务，贵视觉模型只用于必须视觉理解的步骤。
- 使用 prompt caching，并记录真实 token/费用。
- 对大规模生产先用自动渲染验证、小模型打分、URL preflight 等低成本过滤，减少昂贵评测调用。
