## 2. 新增主要结论

当前数据集除了昨天已经确认的语言、敏感域名、patch 唯一匹配问题外，还存在以下明显问题：

1. **text-edit/text-repair 发布 schema 不统一**：输入代码藏在 `instruction` 里，而不是顶层 `input_files`。这会让训练转换、质量审计和后续复查都更容易出错。
2. **所有 edit/repair release 都缺 `output_files`**：四类 edit/repair 的 `replace` 端无法从 release 中复核，`patch_replace_uncheckable_missing_output_files = 100%`。
3. **text-repair patch 问题比昨天以为的更严重**：识别出 hidden input 后，`text-repair` 有 `1,273 / 4,926 = 25.84%` 样本 `search` 找不到。
4. **image-edit/text-edit patch 基本不可直接信任**：`image-edit` 有 `71.22%`、`text-edit` 有 `70.04%` 样本存在 `search` 找不到。
5. **image-repair 有 278 条 src-only 部分成功样本**：`278 / 4,845 = 5.74%` 缺 `dst_screenshot`，不适合需要 before/after 视觉监督的训练口径。
6. **image-repair 前后图差异过小问题很明显**：200 个有 src/dst 的抽样中，`89 / 200 = 44.50%` 的 RMS diff `< 0.005`，其中大量样本是完全 0 差异；median RMS 也只有 `0.0133`。
7. **图片文件本身存在缺失/空文件**：`image-edit` 有 76 条引用图片缺失、1 条空文件；`image-repair` 有 5 条 src/input 空文件、2 条 dst 空文件。
8. **远程依赖残留很重**：大量样本保留远程 script、iframe、stylesheet、font、image URL。尤其 image 任务中 `remote_script_src` 约 89%-91%。
9. **handoff 反馈显示 token 长度已经严重影响训练可用性**：Qwen3-VL tokenizer 实测全量 33,070 条样本时，重任务 p50 已在约 29-33 万 token，p99 到 360-402 万 token；32K/64K cutoff 下绝大多数样本会被截断。
10. **handoff 将超长根因进一步定位为全页自包含归档噪声**：抽样归因显示作者手写 JS 只占约 2-3%，第三方 vendor / 压缩 blob 占 75-79%；大量 `resources/` 文件是孤儿、重复或巨型第三方 blob。
11. **图片替代源形成强任务分布差异**：image 任务几乎全是 `loremflickr`，text 任务几乎全是 `picsum` 残留。这会让模型学到数据构造痕迹。
12. **跨任务同 instance_id 大量重叠**：`image-edit` 和 `text-edit` 完全一一重叠，`image-repair` 和 `text-repair` 完全一一重叠；此外 generate/repair/edit 之间还有 200-386 级别额外重叠。切分 train/eval 时必须按 `instance_id/domain` 分组，否则会泄漏。
13. **最终 release 的来源批次不可追踪**：远端中间数据分散在 full、pilot、retry、hardtimeout、single_runs 等目录，release 内没有逐样本 `source_batch` / `script_version` / `filter_version`。

## 7. 训练方 handoff 反馈补充

本节来自合作者交接包 `webcoding_sft_handoff.tar.gz` 中的 `HANDOFF_data_pipeline.md`、`CONTEXT_HANDLING_NOTES.md` 与 `token_lengths/summary.json`。这部分反馈不是新增静态审计脚本直接得到的结果，而是训练/评测侧在把 release 数据组装成 Qwen3-VL + LLaMA-Factory 训练样本后暴露出来的问题。

### 7.1 token 长度已成为 P0 训练阻塞

handoff 中用 Qwen3-VL tokenizer 对全量 33,070 条样本做了文本 token 统计，尚未计入图片视觉 token。结果显示：

| 任务 | p50 | p99 | max |
|---|---:|---:|---:|
| `text-generate` | 33.1 万 | 402 万 | 1117 万 |
| `text-edit` / `text-repair` | 约 31 万 | 约 390 万 | 约 744 万 |
| `image-edit` / `image-repair` | 约 29 万 | 约 360 万 | 约 742 万 |
| `image-generate` | 6.7 万 | 45.9 万 | 695 万 |

各 cutoff 下完整不截断的样本比例也很低：

| cutoff | 重任务 generate/edit/repair | `image-generate` | 全体 |
|---|---:|---:|---:|
| 32K | 3-4% | 19.9% | 8.5% |
| 64K | 8-10% | 48.9% | 20.6% |
| 128K | 19-22% | 78.8% | 37.5% |
| 256K | 41-47% | 93.5% | 58.3% |

因此，下版数据不能只按“样本是否格式正确”验收，还必须增加 token budget gate。handoff 给出的目标是：清洗后让重任务 p90/p95 落进计划训练 cutoff，理想不超过 64K，最差不超过 128K，并把新的 `token_lengths/summary.json` 交给训练方复核。

### 7.2 超长根因：全页自包含归档中的 vendor / 孤儿资源

handoff 对 text 三类任务各抽样 400 条做了字符归因，结论是：

- 作者手写 JS 只占约 2-3%。
- 第三方 vendor、压缩 blob 占 75-79%。
- HTML，包括内联 CSS/JS，占约 20%。

典型样本 `text-generate` 的 `3dgroup.net` 有 21 个文件、约 179 万字符，其中 `index.html` 本体约 396K，占 22%；20 个 `resources/*.js` 合计 139 万字符，占 78%。单个 `recaptcha__en.js` 就有 893K，占整条样本约 50%。更关键的是，HTML 里 7 个 `<script>` 只有 2 个引用 `resources/`，20 个资源文件中 18 个没有被页面真正引用。

这说明当前 release 的“远程资源与构造痕迹”问题不只是安全/可复现问题，也直接转化成训练 token 成本。下版应把 `resources/` 清洗作为生产数据的必做步骤，而不是训练前临时过滤。

### 7.3 handoff 建议的数据清洗分层

handoff 建议把清洗分成三层：

| 层级 | 处理 | 数据侧要求 |
|---|---|---|
| 层 1：安全清理 | 删除未被本样本 HTML/CSS 文本引用的 `resources/` 孤儿文件；删除完全重复资源 | 必做；保留被删清单，便于回溯 |
| 层 2：外链化 | 对仍被引用的第三方库，如 jQuery、Bootstrap、reCAPTCHA，改为 CDN 外链并删除本地 blob | 需训练/评测方确认 eval/部署是否允许访问 CDN |
| 层 3：永远保留 | HTML、内联 CSS/JS、作者自己的 `.js`/`.css`、任务目标文件 | 不应为了降 token 破坏任务语义 |

引用检测至少要覆盖 `"resources/x"`、`"./resources/x"`、单/双引号、CSS `url(...)` 和裸 hash 串。对动态加载可能会有静态检测误判，因此下版需要同时输出删除清单和抽样可渲染检查结果。

### 7.4 edit / repair 的额外约束

handoff 特别强调：edit / repair 中凡是 `response` 或 `patches` 的 `path` 命中的文件，不能删、不能改，否则 patch 的 `search` 文本会失配，样本直接作废。

结合本报告第 3 节已有结论，下版清洗顺序应为：

1. 先统一 schema，显式保留 `input_files`、`output_files`、`patches`。
2. 对 edit/repair 先验证 patch 可应用性。
3. 对未被 patch 命中的 `resources/` 文件做孤儿/重复清理。
4. 清洗后再次验证 patch `search` 唯一匹配，并重新生成 token 长度统计。

### 7.5 训练格式契约与占位符问题

handoff 说明训练方当前使用 `prompts.py` 将 6 类任务转成 ShareGPT 格式，输入上下文采用 Markdown，assistant label 采用 `<create_file>` / `<edit_file>` XML。数据生产侧清洗时必须保持字段契约不变，否则转换脚本会读不到：

| 任务 | 输入字段 | label 字段 | 图片字段 |
|---|---|---|---|
| `text-generate` | `instruction` | `response = [{path, code}]` | - |
| `image-generate` | 截图输入 | `response = [{path, code}]` | `input_images` / `src_screenshot` |
| `text-edit` | `instruction.description` + `instruction.src_code` | `response = [{path, search, replace}]` | - |
| `image-edit` | 同 text-edit | 同 text-edit | `input_images` / `src_screenshot` |
| `text-repair` | `instruction` 或 `input_files` | `response` / `patches` | - |
| `image-repair` | `instruction` 或 `input_files` | `response` / `patches` | `src_screenshot` + 可选 `dst_screenshot` |

另外，网页代码中天然可能出现 `<image>`、`<video>`、`<audio>` 标签。LLaMA-Factory 的多模态校验会统计这些占位符数量，如果直接用默认 `<image>`，会和网页代码冲突。handoff 已将截图占位符改为 `<training_image_holder>`，并要求训练/推理前设置：

```bash
export IMAGE_PLACEHOLDER='<training_image_holder>'
export VIDEO_PLACEHOLDER='<training_video_holder>'
export AUDIO_PLACEHOLDER='<training_audio_holder>'
```

数据侧需要避免把这些 sentinel 当作普通网页内容写入代码，并在交付时保证图片路径真实存在；`export_sharegpt.py` 会自动剔除缺图条目并输出 dropped 清单。

### 7.6 handoff 对交付物的要求

除本报告已有 full audit / QC 产物外，handoff 要求清洗后额外交付：

- 洗后的 6 类 JSONL，字段契约保持不变。
- `out/*.sharegpt.jsonl` 组装产物。
- `out/*.dropped.json` 缺图丢弃清单。
- 新的 `token_lengths/summary.json`。
- 每层清洗删了多少、留存率多少的简表。
- 被删资源清单。

验收时至少要跑通 `prompts.py` 冒烟、`export_sharegpt.py --all`、`analyze_token_lengths.py`，并抽查 HTML 是否仍能引用保留资源、edit/repair patch 文件是否还在。

## 9. 重复与泄漏风险

统计结果：

- duplicate instance_id groups：9,038 组，涉及 19,733 条样本。
- 同任务内没有 duplicate instance_id。
- 主要是跨任务共享：
  - `image-edit` 与 `text-edit`：4,333 条完全重叠。
  - `image-repair` 与 `text-repair`：4,845 条完全重叠。
  - 其他任务对之间还有 200-386 条级别的重叠。
- duplicate target-code hash：472 组，涉及 985 条样本。

解释：

- edit/image-edit、repair/image-repair 的一一重叠是任务设计导致的，不一定错误。
- 但如果后续切分训练/验证/测试时不按 `instance_id` 或 domain 分组，会产生严重泄漏。
- duplicate code hash 需要二次查：可能是同模板站点，也可能是重复页面或空模板。

下版建议：

- 所有 split 必须 group by `instance_id` / normalized domain。
- 训练前输出 overlap report。
- 对 duplicate code hash 的样本做 cap 或去重。

## 10. Schema 与可追踪性问题

当前 release schema 有几处不利于复查：

1. `text-edit/text-repair` 没有顶层 `input_files`，输入代码放在 `instruction` 中。
2. 四类 edit/repair 均缺顶层 `output_files`，导致 replace 端无法复核。
3. `response` 在 generation 中是 code files，在 edit/repair 中是 patches，字段语义随任务变化。
4. `patches` 与 `response` 在部分任务中重复表达同一内容。
5. release 样本没有记录完整来源批次，例如 full、retry、hardtimeout、single_run。

下版建议统一：

```text
instance_id
task
input_files
output_files
patches
input_images
src_screenshot
dst_screenshot
source_url
source_domain
source_batch
script_version
filter_version
conversion_status
qc_status
qc_issues
```

轻量训练版可以裁剪，但 full audit 版必须保留。

## 11. 下版构造前必须加的 Gate

### P0 hard reject

- 非 zh/en 页面。
- adult / porn / escort / dating / casino / betting / gambling 等风险 domain/path/title/h1。
- captcha / Cloudflare / access denied / parked / domain-for-sale / default server / 404/403/500。
- patch `search` 不存在、多重匹配、为空、过短、`search == replace`。
- 应用 patch 后不能得到目标 `output_files`。
- image task 引用图片缺失、空文件、解码失败。
- image-repair 需要 after 图时，剔除 `partial_success_src_screenshot_only`。
- remote script / iframe / stylesheet / font 未 localize 或未移除。
- `resources/` 中未被本样本 HTML/CSS/JS 引用的孤儿文件未清理，或清理后没有删除清单。
- 清洗后重任务 p90/p95 仍明显超过目标训练 cutoff，且没有按长度过滤/分桶方案处理。
- 危险协议 `javascript:` / `data:text/html`。

### P1 repair or normalize

- `src/srcset=null/#/about:blank`。
- `loremflickr` / `picsum` 构造指纹不一致。
- 可见文本过少。
- duplicate code hash。
- 过重 head / body 出现太晚。
- 第三方 vendor blob、重复资源、reCAPTCHA/embed/analytics 等大体积非作者代码未外链化或未剔除。
- schema 字段不统一。

### P2 audit-only / 抽查

- 普通外链 `<a href>`。
- inline event handler。
- remote image 是否允许保留。
- image-repair before/after 差异。
- 近纯色/全白/全黑截图。
- 清洗后 token 分布与留存率。

## 12. 建议的下一步

1. 先实现统一 QC gate，输出 `accepted.jsonl`、`rejected.jsonl`、`reject_reasons.jsonl`。
2. 回到 full unified 数据重算 edit/repair patch，并保留 `output_files`。
3. 统一图片替代与资源 localize 策略，不要 text 用 picsum、image 用 loremflickr。
4. release 前按 domain/instance 分组切分，生成 leakage report。
5. 补跑视觉 QC：空白/纯色/尺寸异常和 image-repair diff。
6. 按 handoff 建议实现 `resources/` 去孤儿/去重，保护 edit/repair patch 命中文件，并输出被删资源清单。
7. 清洗后重新导出 ShareGPT 训练样本，跑 token 长度统计，确认重任务 p90/p95 进入目标 cutoff。
8. 与训练/评测方确认是否允许 CDN 外链；若允许，再做第三方库外链化，否则只做安全清理并配合长度过滤。
