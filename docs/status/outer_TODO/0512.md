## 5. 我建议你现在先把主线收窄成两层

### 第一层：先把 generation 彻底做通

原因：

- 这是最接近量产的部分。
- 也是后续 editing / repair 的 clean site 质量基线。

这一层的目标应该非常具体：

1. 修复 generate v2 的 `EPIPE`

### 第二层：把 edit / repair 从 prototype 变成 pipeline

这一层不要一上来追 10k，先追“统一入口 + 统一 schema + 可验证”。

目标应该是：

2. 统一 `src_code / dst_code / label_modified_files / resources / screenshots`
3. 先跑小规模 20 条 text-editing / image-editing / text-repair / image-repair
4. 抽检后再放大

## 6. 现在最值得冻结的几个决定

### 决定 A：七类任务里，video 只属于 generation

目前文档里最稳定的七类就是：

- 3 个 generation: text / image / video
- 2 个 editing: text / image
- 2 个 repair: text / image

先不要扩成 video-editing / video-repair，不然复杂度会失控。

### 决定 B：`sp/mp` 只作为 editing / repair 的属性

不要把它和七类任务并列。

### 决定 C：edit/repair 的 text 与 image 共享同一份底层 pair

也就是：

- text-editing 和 image-editing 共用同一批 `src -> dst`
- text-repair 和 image-repair 共用同一批 `broken -> clean`

这样你真正要构造的底层样本类型其实只有 5 种，而不是 7 条完全独立的线：

1. text-generation pair
2. image-generation pair
3. video-generation pair
4. editing pair
5. repair pair

image 版本只是多挂视觉输入。

### 决定 D：先冻结 schema，再继续大规模跑数

这个决定很重要，因为你现在最大的风险不是“数量不够”，而是“跑出一堆以后发现格式不统一，要返工”。

## 8. 你今天这页里原本的灵感，应该放在哪

你写的这几条其实不是主线数据构造，而是“第二阶段增强方向”：

- 特别长文件的筛选逻辑
- Playwright 可渲染样本的小模型打分
- 静态网页之外的特效设计
- 利用截图差异让模型学会发现设计不足
- 构造前端展示差异 + 交互差异 case，让模型学会找不同

这些想法是有价值的，但更适合挂到下面两个分支：

### 分支 1：数据筛选 / 质量控制

- 过长文件过滤
- 渲染成功检测
- 小模型视觉质量打分

### 分支 2：高级 repair / self-critique / difference modeling

- 截图差异发现
- 视觉缺陷诊断
- 动效与交互差异建模

也就是说，这些不是“先做的主线”，而是“主线打通后的增强版”。

## 9. 我给你的最短结论

你当前项目最核心的问题只有一句话：

“七类任务定义已经有了，但 generation 产线还没彻底跑通，edit/repair 还没从原型统一成正式 schema 和批量入口。”

所以接下来最合理的顺序是：

1. 冻结七类 schema
2. 修复并跑通 generation v2/v3
3. 把 edit/repair 合成统一入口
4. 再考虑视觉差异、自诊断、特效这类增强方向
