# 从爬取到训练样本的全流程筛选与处理方案

> 日期：2026-07-01  
> 适用对象：WebCoding 六任务 SFT 数据生产线  
> 目标：把最初爬取/导入的网页样本，经过可追踪的筛选、清洗、构造、审计和训练格式转换，变成真正可以进入训练的样本。  
> 参考来源：当前代码逻辑、`docs/status/remote_quality_audit_20260630/当前数据集新增质量审计报告.md`、合作者 handoff 包 `webcoding_sft_handoff.tar.gz`。

## 0. 核心原则

最终训练样本必须同时满足五类约束：

1. **内容安全与任务有效**：不含成人、博彩、约会、escort、casino、porn 等风险站点；不是 captcha、Cloudflare、parked domain、默认服务器页、404/403/500、低信息页面。
2. **代码监督可执行**：generation 有完整目标代码；edit/repair 的 patch 必须能唯一匹配输入，应用后能得到输出，`replace` 能在输出代码中复核。
3. **视觉监督真实可用**：图片文件存在、可解码、非空白/纯色；image-repair 的 before/after 差异足够支撑视觉训练，否则降级或剔除。
4. **训练长度可承受**：不能把全页归档噪声、孤儿 `resources/`、第三方 vendor blob 全塞进上下文；清洗后重任务 p90/p95 应落进目标 cutoff，理想不超过 64K，最差不超过 128K。
5. **可追踪可复查**：每条样本保留 `instance_id`、来源批次、脚本版本、过滤版本、QC 状态、拒绝原因和关键中间产物。轻量训练版可以裁剪，但 full audit 版必须可复现。

当前 release 暴露的问题说明：只做到“能爬下来、能转 JSONL”不够。生产线必须把 QC gate 前移到爬取、清洗、构造和发布前，而不是等训练方发现 token 爆炸、patch 失配和图片缺失。

## 1. 目标数据形态

当前主线为 6 类任务：

| 任务 | 输入 | 输出 / 监督 |
|---|---|---|
| `text-generate` | 文本设计文档 / PRD | 完整网页代码 `response=[{path, code}]` |
| `image-generate` | 目标截图 | 完整网页代码 `response=[{path, code}]` |
| `text-edit` | 编辑前代码 + 编辑指令 | search/replace patches |
| `image-edit` | 编辑前代码 + 编辑指令 + 编辑前截图 | search/replace patches |
| `text-repair` | buggy 代码 | buggy -> fixed patches |
| `image-repair` | buggy 代码 + buggy 截图 + fixed 截图 | buggy -> fixed patches |

推荐内部 full schema：

```text
instance_id
task
page_type
input_files
output_files
patches
instruction
input_images
src_screenshot
dst_screenshot
source_url
source_domain
source_batch
script_version
filter_version
conversion_status
qc_status
qc_issues
deleted_resources
token_stats
metadata
```

对外轻量训练版可以根据任务兼容旧字段，但 full audit 版必须保留 `input_files` / `output_files` / `patches`，否则 patch 监督无法复核。

## 2. 总体流程

```text
URL / 原始项目
  -> URL 形态过滤
  -> HTTP preflight
  -> Playwright 爬取 / WebRenderBench expand
  -> 页面级 postprocess
  -> 资源本地化与去噪
  -> 项目级 QC
  -> 任务构造
  -> patch normalize 与可执行性校验
  -> 图片任务截图与视觉 QC
  -> release schema 统一
  -> release 深度审计
  -> handoff 要求的资源瘦身与 token 自检
  -> ShareGPT / LLaMA-Factory 转换
  -> 进入训练
```

每个阶段都输出：

- `accepted.jsonl`：进入下一阶段。
- `rejected.jsonl`：明确拒绝，不再重跑。
- `retry.jsonl`：网络、超时、临时资源失败，可单独补跑。
- `reject_reasons.jsonl`：逐样本原因，支持统计和回溯。

## 3. 阶段一：URL 与原始样本入口过滤

### 3.1 已有逻辑

`preprocess/filter_webcode2m_urls.py` 已经实现第一层 URL 形态过滤：

- 去重 host。
- 拒绝明显的统计/CDN/广告/静态资源/临时托管域名。
- 拒绝过长 host、异常字符、路径 URL、随机 hash 样域名、过多子域名、低优先级 TLD。
- 对保留 URL 做确定性 shuffle，避免按字典序集中抽到数字域名和低质站。

### 3.2 新增必须 gate

URL 入口阶段就应增加内容和安全黑名单，不等页面落盘：

- adult / porn / porno / xxx / nude / erotic / webcam / bdsm。
- escort / call-girls / hookup / dating。
- casino / gambling / betting / bet。
- domain/path 中明显的 parked、free hosting、temporary、placeholder。
- 已知高风险来源批次或失败重跑批次应带 `source_batch`，不能混进 release 后失去追踪。

### 3.3 输出要求

保留 `url_filter_report.json`：

```text
input_count
kept_count
rejected_count_by_reason
seed
filter_version
```

所有后续样本都继承 `source_url`、`source_domain`、`url_filter_version`。

## 4. 阶段二：HTTP Preflight

### 4.1 已有逻辑

`preprocess/preflight_webcode2m_urls.py` 已经用便宜 HTTP 请求剔除：

- HTTP 4xx/5xx。
- 非 HTML / XML / text 页面。
- 缺少 HTML 结构 hint 的响应。
- challenge / captcha / access denied。
- parked domain / domain for sale。
- default server / coming soon / under construction / account suspended。
- 可见文本过少。

### 4.2 新增必须 gate

preflight 应补强：

- 正文语言检测：只保留中文/英文。`<html lang>` 只能作 hint，不能当最终判断。
- `title` / `h1` / meta description / URL path 联合风险词 hard reject。
- 明确区分 `retryable_network_error` 和 `hard_reject_content`。
- 记录 redirect 链路，若跳到 parked、广告、login、安全检查域名，直接拒绝。

### 4.3 输出要求

保留：

- `preflight_passed_urls.txt`
- `preflight_rejected.jsonl`
- `preflight_report.json`

`preflight_rejected.jsonl` 至少包括：

```text
url
final_url
status_code
content_type
text_chars
reason
marker
elapsed_sec
```

## 5. 阶段三：Playwright 爬取与 WebRenderBench Expand

### 5.1 已有逻辑

当前有两条入口：

- WebRenderBench：`pipeline_a_sample_level.py` / `playwright_crawl.py expand`，从已有项目扩展多页。
- WebCode2M：`pipeline_b_sample_level.py` / `playwright_crawl.py crawl`，用 Playwright 打开真实站点，抓首页和导航子页。

已有能力：

- `--max-pages` 控制子页数量。
- `--wait` 等待渲染。
- `--site-timeout` 用独立进程硬超时，超时后清理。
- manifest 支持断点续跑。
- status 包括 `single_page`、`multi_page`、`site_timeout`、`empty_page`、`wrong_language`、`challenge_page` 等。

### 5.2 新增必须 gate

爬取阶段不要只看是否打开成功，还要记录页面质量：

- 首页和每个子页的 HTTP 状态、最终 URL、标题、语言、可见文本长度。
- 是否命中 challenge / access denied / parked / default server / low visible text。
- 页面数量、导航链接数量、实际加入子页数量。
- 页面主内容是否过少：可见文本 `<80` 或 HTML tag `<8` 进入 reject/review。
- 记录 Playwright console error / page error，但不要只因少量 favicon 或 third-party error 拒绝。

### 5.3 输出要求

每个 project 目录应包含：

```text
index.html
*.html
resources/
metadata.json
crawl_quality.json
```

`metadata.json` 需要写入：

```text
source_url
source_domain
source_batch
crawl_status
pages_added
has_single_page
has_multi_page
crawl_script_version
filter_version
```

## 6. 阶段四：页面 Postprocess 与基础资源清洗

### 6.1 已有逻辑

`preprocess/postprocess_webcode2m_crawl.py` 已经做：

- 检测 challenge markers。
- 将 challenge 项目移动到 quarantine。
- 删除 analytics/tracking script。
- 若本地 analytics JS 不再被引用，则删除对应文件。

`preprocess/playwright_crawl.py localize_resources()` 已经做：

- 去掉 IE conditional comments 和 HTML comments。
- 修复 LiteSpeed script type。
- 删除 tracking / analytics scripts。
- 下载非 tracking 远程 JS 到 `resources/`，下载失败则移除。
- 清理 `srcset`、lazy load 属性、CKEditor 残留。
- 移除 off-canvas、过长 carousel 多余 slide。
- 移除 iframe。
- 移除远程 video / audio。
- 清理空容器高度。
- 处理 CSS `url(...)` 中的字体等非图片资源。
- 内联或下载剩余远程 CSS。

### 6.2 新增必须 gate

当前质量报告显示 release 中远程依赖残留仍很重，因此清洗后必须做硬校验：

- `remote script / iframe / stylesheet / font` 默认 reject 或 localize。
- `javascript:`、`data:text/html`、`vbscript:` 直接 reject。
- `src/srcset=null/#/about:blank` 必须清理。
- 普通 `<a href>` 可保留、中和或单独统计，但不能和资源依赖混在一个指标里。
- 新版本禁止合成图片占位 URL：不再把原始链接替换成 `picsum`、`loremflickr` 或其他占位服务；图片要么真实本地化，要么保留原始 URL 并交给 QC 判定。

### 6.3 handoff 新增：训练前资源瘦身

合作者 handoff 指出 token 爆炸的主因是全页自包含归档里的 vendor / 孤儿资源：

- 作者手写 JS 约 2-3%。
- 第三方 vendor / 压缩 blob 占 75-79%。
- 大量 `resources/*.js` 没有被任何 HTML/CSS 引用。
- 典型样本中单个 `recaptcha__en.js` 可占整条样本约 50%。

因此资源清洗必须新增一层“训练瘦身”：

| 层级 | 处理 | 规则 |
|---|---|---|
| 安全清理 | 删除孤儿 `resources/` 文件和完全重复资源 | 可自动执行；保留删除清单 |
| 外链化 | 对仍被引用的第三方库改 CDN 外链，删本地 blob | 需确认 eval/部署允许 CDN，且必须提供显式映射 |
| 永久保留 | HTML、内联 CSS/JS、作者自己的 `.js`/`.css`、patch 命中文件 | 不为了降 token 破坏任务 |

通俗解释：

- “孤儿资源”就是放在 `resources/` 里但网页根本没有引用的文件。模型训练时把它塞进去只会涨 token，不会影响页面效果，删除最安全。
- “重复资源”就是内容 hash 完全一样的文件，只保留第一份即可。
- “被引用的第三方库/blob”是页面真的引用了的巨大库文件，例如 reCAPTCHA、analytics、压缩后的 vendor bundle。它们不是作者写的目标代码，不适合塞进训练上下文；但直接删除会让页面或截图变坏，所以只能在允许 CDN/外链时，把本地引用改回稳定 CDN URL。
- “HTML + 内联 CSS/JS + 作者脚本”才是模型应该学习生成/编辑/修复的东西，必须保留。

第三方库识别不能假设全自动可靠，应按置信度分层：

| 类型 | 例子 | 处理 |
|---|---|---|
| 明确第三方库 | `jquery.min.js`、`bootstrap.min.css`、`fontawesome.css`、`recaptcha__en.js`、`lodash.min.js` | 可生成 CDN 候选映射，确认后外链化 |
| 疑似第三方 blob | `vendor.js`、`chunk-vendors.js`、`bundle.min.js`、`embed.php.js`、大体积压缩 JS/CSS | 只标记为 `vendor_or_blob` / `suspected_vendor_blob`，默认不改 |
| 混合 bundle / 作者代码 | `main.js`、`app.js`、`theme.css`、包含站点配置或业务逻辑的压缩文件 | 保留，不自动外链化 |

外链化不是强行“还原原始 URL”，而是把可确认的第三方库改成稳定 CDN 引用。如果版本号、来源或是否混入作者代码无法确定，宁可保留并统计 token 风险，也不要误删/误外链导致样本语义损坏。

孤儿检测至少覆盖：

- `"resources/x"`、`"./resources/x"`。
- 单引号、双引号、无引号。
- CSS `url(...)`。
- 文件名和 hash 裸串。

edit/repair 额外约束：凡是 `response` / `patches` 中 `path` 命中的文件，不能删、不能改，否则 patch `search` 会失配。

当前实现：

- `utils/webcoding_pipeline/resources.py`：审计孤儿、重复、被引用 vendor/blob、作者代码。
- `scripts/slim_project_resources.py`：默认只审计；传 `--apply` 后删除孤儿/重复；只有同时传 `--allow-cdn-externalize` 和 `--externalize-map` 时才外链化第三方 blob。

推荐执行顺序：

1. 先跑只读审计，产出 orphan / duplicate / vendor_or_blob 清单。
2. 自动应用 orphan / duplicate 删除。
3. 对明确第三方库生成候选 `externalize-map`。
4. 人工确认 CDN 是否允许、映射是否正确。
5. 只有确认后才对 referenced vendor/blob 做外链化。
6. 每层处理后重新跑 token 分布与抽样渲染。

### 6.4 输出要求

每个项目新增：

```text

deleted_resources.json
remote_dependency_report.json
```

`deleted_resources.json` 应记录：

```text

reason: orphan | duplicate | externalized_vendor | tracking

content_hash
referenced_by

```

## 7. 阶段五：项目级 QC

项目进入任务构造前，必须通过统一项目 QC。

### 7.1 P0 hard reject

- 非中文/英文页面。
- adult / porn / escort / dating / casino / betting / gambling 风险域名、路径、title、h1、正文。
- captcha / Cloudflare / access denied / security check。
- parked / domain-for-sale / under construction。
- default server / 404 / 403 / 500。
- 可见文本过少。
- 远程 script / iframe / stylesheet / font 未 localize 或未移除。
- 危险协议 `javascript:` / `data:text/html` / `vbscript:`。
- `src/srcset=null/#/about:blank` 未清理。
- 资源清理后 HTML 引用丢失。
- 项目代码过短、缺 `<html>` / `<body>`，或无有效 HTML 文件。

### 7.2 P1 repair or normalize

- 普通远程图片：localize 或统一替代。
- 普通外链 `<a href>`：中和或标记。
- inline event handler：审计记录，必要时保留。
- 过重 head / body 出现太晚：压缩 head、去 vendor、去孤儿。
- duplicate code hash：去重或 cap。
- schema 字段不统一：转 unified schema。

### 7.3 输出要求

项目级 QC 输出：

```text
project_qc.accepted.jsonl
project_qc.rejected.jsonl
project_qc.retry.jsonl
project_qc_summary.md
```

进入构造的项目必须有 `qc_status=accepted`。

## 8. 阶段六：任务构造

### 8.1 Generation

`text-generate`：

- 输入为 PRD / 设计文档。
- 输出为完整代码文件。
- PRD 生成逻辑参考 `construct_common.py` 中的 `TEXT_PRD_PROMPT`、`CODE_PRD_PROMPT`。
- PRD 不应暴露“截图、源码、benchmark、数据集”等内部来源。

`image-generate`：

- 输入为目标截图。
- 输出为完整代码文件。
- 图片路径必须相对 task 目录且真实存在。

#### 8.1.1 handoff 新增：`text-generate` 与 `image-generate` 代码面不一致

合作者指出当前 release 中 `image-generate` 和 `text-generate` 的目标代码面可能不一致：

- `text-generate` 来自 OSS / full code 数据，往往带很多 `resources` 和多文件上下文。
- `image-generate` 当前 release 来源是 `output_full/fake_url/image-generate`，构造脚本 `scripts/build_fake_url_image_generation_dataset.py` 只读取 `index.html`，并写入 `resources: []`，所以通常只有 HTML。

这会带来两个问题：

1. token 分布不可直接比较：`image-generate` 短，不一定代表任务天然短，而是构造代码面更轻。
2. 训练目标不一致：同样是 generate，text 任务让模型学“多文件/带 resources 的网页”，image 任务让模型学“单 HTML 网页”，模型会收到混合信号。

处理原则：

- release 前必须记录每个任务的 `target_format`：`single_html`、`multi_file_with_resources`、`slimmed_multi_file` 等。
- 最终训练版应尽量统一 generate 任务的目标代码策略。推荐策略是：两类 generate 都走资源瘦身后的同一代码面，即保留 HTML、作者 CSS/JS，删除孤儿/重复资源，第三方库仅确认后外链化。
- 若短期内无法重构 `image-generate`，必须在报告中标记它是 `single_html` 特例，不要把它的 token 统计当作 full-code generate 的代表。
- 后续修复方向二选一：
  - 从同一批 full project 重新构造 `image-generate`，让它和 `text-generate` 一样保留瘦身后的必要文件。
  - 或把 `text-generate` 也转换为统一的 lightweight/single-html 训练目标，但这会改变任务定义，需要单独决策。

Generation gate：

- `response` 中每个 item 必须有 `path` 和 `code`。
- 至少包含可渲染入口，如 `index.html`。
- 目标代码不能是空 body / 极短模板 / challenge 页。
- 输出代码中的 remote script / iframe / font 继续按项目 QC 处理。
- `text-generate` 与 `image-generate` 必须输出 `target_format` / `code_surface` 统计；若两者策略不同，release report 必须显式说明。

### 8.2 Edit

已有逻辑：

- `normalize_oss_webcoding_jsonl.py` 从旧字段中读取 `instruction.src_code` 和 `response`。
- `apply_patch_items()` 对 patch 做 `exact`、`html_unescape`、`strip_cdata` 等匹配变换。
- patch 必须在输入文件中唯一匹配。
- 应用 patch 后生成 `output_files`。
- 历史脚本 `replace_picsum_with_loremflickr.py` 仅用于旧数据排查；新版本不做图片 URL 替换，patch 复核必须基于原始链接或真实本地化后的代码。

Edit gate：

- `path` 必须存在于 `input_files`。
- `search` 非空、足够长、唯一匹配。
- `replace` 非空，且应用后可在 `output_files` 找到。
- `search != replace`。
- patch 数量不能为 0。
- 修改不能超出任务说明范围；这项可以先抽查，后续再自动化。

`image-edit` 在 `text-edit` 基础上增加 src screenshot。质量报告确认 `image-edit` 和 `text-edit` instance 完全重叠，这是任务设计允许的，但 split 必须按 `instance_id/domain` 分组。

### 8.3 Repair

已有逻辑：

- `normalize_oss_webcoding_jsonl.py apply_repair_patch_items()` 支持两种输入：
  - 输入已经是 buggy：直接输出 buggy -> fixed。
  - 输入是 clean：反向注入 bug，再统一输出 buggy -> fixed。
- 最终会复核 normalized `search` 在 buggy input 中、`replace` 在 fixed output 中。

Repair gate：

- `task_type` 保留，用于缺陷数量和统计，但训练 prompt 不直接告诉具体缺陷类型。
- buggy input 和 fixed output 都必须保留在 full audit 版。
- patch 必须可应用、可复核。
- 对视觉不可见缺陷，如部分 Missing Attributes，可进入 text-repair，但不一定适合 image-repair。

`image-repair` 在 `text-repair` 基础上增加 buggy src screenshot 和 fixed dst screenshot。

## 9. 阶段七：截图、图片与视觉 QC

### 9.1 已有逻辑

`construct_image_editing.py`：

- 复制 text-editing 实例。
- 对原始 source project 截图，写入 `src_screenshot`。

`construct_image_repair.py`：

- 复制 text-repair 实例。
- 对 clean source project 截图为 `dst_screenshot`。
- 反向应用 patch 得到 defective project。
- 对 defective project 截图为 `src_screenshot`。

已有补救策略：

- 触发 lazy load 和滚动。
- 处理 `srcset=null/#` 等坏候选。
- 图片 URL 不再统一替换；只保留原始链接或真实下载后的本地资源路径。
- 设置 `PW_TEST_SCREENSHOT_NO_FONTS_READY=1` 避免等待字体卡死。
- 对 hard timeout 单样本子进程重跑。

### 9.2 新增必须 gate

图片文件：

- 引用路径必须存在。
- 文件大小 > 0。
- 可被 PIL 解码。
- 尺寸不能过小。
- 非全白、全黑、近纯色。

image-repair before/after：

- 如果训练口径需要 before/after 视觉监督，缺 `dst_screenshot` 的 src-only 样本直接剔除 image-repair。
- 计算 RMS diff 和 changed pixel ratio。
- RMS `<0.005` 优先剔除或降级为 text-repair。
- RMS `0.005-0.02` 进入抽查或按 defect type 细分。
- 对视觉天然不明显的 defect type，默认不作为 image-repair 的核心训练样本。

### 9.3 输出要求

```text

image_qc.md
image_repair_diff.jsonl
image_repair_diff_summary.json
```

每条 image 样本写入：

```text

image_qc_issues
src_dst_rms_diff
changed_pixel_ratio
```

## 11. 阶段九：深度审计与最终 Gate

### 11.1 已有逻辑

`scripts/deep_release_quality_audit.py` 已经统计：

- JSON parse。
- task 字段匹配。
- `instance_id` 缺失。
- risky instance/path。

- image-repair 缺 dst。
- duplicate instance_id、duplicate target code hash、duplicate image reference。

### 11.2 最终 P0 hard reject

发布进入训练前，以下任一命中即不能进入训练：

- 非 zh/en。
- 风险内容或风险域名/path/title/h1。
- challenge、captcha、access denied。
- parked、domain-for-sale、under construction。
- default server、404、403、500。
- patch `search` 不存在、多重匹配、为空、过短、`search == replace`。
- 应用 patch 后不能得到 `output_files`。
- `replace` 不能在 `output_files` 中找到。
- 图片缺失、空文件、解码失败。
- image-repair 缺 after 图但任务口径需要 before/after。
- image-repair diff 过低且无法解释。
- remote script / iframe / stylesheet / font 未 localize 或未移除。
- `resources/` 孤儿文件未清理，或清理后没有删除清单。
- 危险协议。
- 清洗后 token 长度明显超过目标 cutoff，且没有过滤/分桶方案。

### 11.3 P1 normalize / repair

- `src/srcset=null/#/about:blank`。
- `picsum` / `loremflickr` / 合成占位图片 URL 残留。
- 可见文本过少但可能是合法 landing page。
- duplicate code hash。
- 过重 head / body 出现太晚。
- 第三方 vendor blob、重复资源、reCAPTCHA/embed/analytics 大体积非作者代码。
- schema 字段不统一。

### 11.4 P2 audit-only

- 普通外链 `<a href>`。
- inline event handler。
- remote image 是否允许保留。
- image-repair before/after 小差异样本抽查。
- token 分布和留存率。

## 12. 阶段十：Token 自检与训练格式转换

### 12.1 handoff 发现的问题

合作者 handoff 用 Qwen3-VL tokenizer 对全量 33,070 条样本统计，尚未计入图片视觉 token：

| 任务 | p50 | p99 | max |
|---|---:|---:|---:|
| `text-generate` | 33.1 万 | 402 万 | 1117 万 |
| `text-edit` / `text-repair` | 约 31 万 | 约 390 万 | 约 744 万 |
| `image-edit` / `image-repair` | 约 29 万 | 约 360 万 | 约 742 万 |
| `image-generate` | 6.7 万 | 45.9 万 | 695 万 |

32K/64K cutoff 下大多数重任务样本会被截断。这个问题必须在数据生产侧解决，而不是训练时硬截断。

### 12.2 训练格式契约

handoff 当前训练转换采用：

- 输入上下文：Markdown。
- assistant label：`<create_file>` / `<edit_file>` XML。
- image placeholder：`<training_image_holder>`，避免与网页代码里的 `<image>` 标签冲突。
- 训练/推理必须设置：

```bash
export IMAGE_PLACEHOLDER='<training_image_holder>'
export VIDEO_PLACEHOLDER='<training_video_holder>'
export AUDIO_PLACEHOLDER='<training_audio_holder>'
```

数据侧必须保证：

- 图片路径真实存在。
- 不把 `<training_image_holder>` 等 sentinel 当普通网页内容写进代码。
- `instance_id` 不变，便于对账。
- repair 的 `task_type` 不被清洗掉。
- 空 `search` 若表示新建文件，要在转换层明确转为 create file，不能混成普通 edit。

### 12.3 输出要求

清洗后交给训练方：

```text
cleaned_full_release/
train_release/
out/*.sharegpt.jsonl
out/*.dropped.json
token_lengths/summary.json
deleted_resources.jsonl
cleaning_retention_report.md
deep_quality_audit.md
sample_issues.jsonl
```

`cleaning_retention_report.md` 至少包括：

- 每任务输入条数。
- 每个 gate reject 条数和比例。
- 资源清理删除文件数、删除字节数。
- token p50/p90/p95/p99/max。
- 各 cutoff 下完整不截断比例。
- 图片缺失剔除数。
- 最终进入训练条数。

## 13. Split 与泄漏控制

当前审计发现：

- `image-edit` 与 `text-edit` 完全一一重叠。
- `image-repair` 与 `text-repair` 完全一一重叠。
- generate/edit/repair 之间还有额外 instance 级重叠。
- duplicate instance_id groups 涉及大量样本。

规则：

- 所有 train/val/test split 必须 group by normalized domain 或 `instance_id`。
- 同一 `instance_id` 不得跨 split。
- 同一 normalized domain 原则上不跨 split；若样本不足，需要输出例外清单。
- release 前生成 overlap report。
- duplicate target-code hash 做 cap 或去重，避免模板站点过度重复。

## 14. 推荐实现顺序

### 第一优先级：堵住训练不可用问题

1. 统一 full schema，补齐 `input_files`、`output_files`、`patches`、`source_batch`、`script_version`、`filter_version`。
2. 对 edit/repair 重跑 patch normalize，确保 `search` 唯一匹配、`replace` 可复核。
3. 实现 `resources/` 去孤儿/去重，保护 patch 命中文件，输出删除清单。
4. 跑 token 统计，确认重任务 p90/p95 是否进入目标 cutoff。

### 第二优先级：堵住质量和安全风险

1. URL/preflight 增加风险词和语言检测。
2. 项目级 QC 拒绝 challenge、parked、default server、低信息页面。
3. 图片 QC 全量跑缺失、空文件、解码、近纯色、尺寸异常。
4. image-repair 全量跑 before/after diff。

### 第三优先级：提高发布可维护性

1. release 分 full audit 版和 train lightweight 版。
2. 所有阶段输出 accepted/rejected/retry 和 summary。
3. split 按 domain/instance 分组。
4. 每次 release 自动生成 handoff 包给训练方。

## 15. 最终进入训练的判定

一条样本只有同时满足以下条件，才允许进入训练：

```text
qc_status == accepted
conversion_status == success
schema_valid == true
content_risk == none
language in {zh, en}
not challenge_or_parked_or_error_page
remote_blocking_dependencies == none
patch_valid == true            # edit / repair
images_valid == true           # image tasks
image_repair_diff_valid == true or task != image-repair
token_length <= configured_policy
split_group_clean == true
```

其中 `configured_policy` 不能只写成“训练时截断”。必须在 release 里明确：

- 直接保留。
- 经资源瘦身后保留。
- 长度分桶保留。
- 超长剔除。

## 17. 当前版本的结论

现有代码已经有不少正确基础：URL 形态过滤、HTTP preflight、challenge quarantine、analytics 清理、patch normalize、真实图片链接保留/本地化、截图 hard timeout、release 打包和深度审计。

但当前质量报告和 handoff 共同说明，还缺三道关键闸门：

1. **生产侧资源瘦身闸门**：去掉孤儿/重复/vendor blob，否则 token 长度让训练不可用。
2. **full schema 与 patch 可复核闸门**：没有 `output_files` 就无法证明 edit/repair 监督正确。
3. **视觉与内容质量闸门**：图片缺失/空白、image-repair 差异过小、风险页面和 challenge 页面必须在 release 前剔除。

下一个可执行里程碑应是：从当前 release 回到 full unified 数据，补齐 schema，重跑 patch gate、资源瘦身 gate、图片 gate 和 token gate，然后再生成新的训练 release。
