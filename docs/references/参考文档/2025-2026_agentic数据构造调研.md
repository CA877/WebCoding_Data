# 数据构造方法调研

## 1. SWE / Coding Agent 数据构造

### 1.1 SWE-Playground: Training Versatile Coding Agents in Synthetic Environments

论文：Training Versatile Coding Agents in Synthetic Environments  
链接：https://arxiv.org/abs/2512.12216

图：SWE-Playground 数据构造 pipeline。

![SWE-Playground 数据构造 pipeline](assets/agentic_data_pipelines/figures/swe_playground_pipeline_page4.png)

#### 要解决的问题

过去 SWE agent 数据主要来自真实 GitHub issues 或 PRs。这类数据有两个限制：

1. 依赖已有仓库，数据分布受真实开源项目限制；
2. 多数任务集中在 issue resolving，不能覆盖更广泛的软件工程能力，比如从零实现一个库、为 bug 写复现测试、改 API、设计模块接口等。

SWE-Playground 的核心思想是：不要等真实仓库提供任务，而是从零合成一个可执行的软件工程环境，再从这个环境中派生任务、测试和轨迹。

#### 数据构造方案

它的数据生产流程可以概括为：

```text
1. 合成软件项目
   - 由强模型生成一个小型但完整的软件工程项目；
   - 项目包含源代码、模块结构、依赖说明、可运行入口；
   - 项目不是单个函数，而是有一定工程结构的环境。

2. 合成任务
   - 基于项目生成多类 SWE 任务；
   - 不局限于 bug fixing，也包括实现新功能、补单元测试、复现问题、从零实现 library 等；
   - 任务描述要和当前项目状态一致。

3. 合成 starter code / hidden target
   - 为任务准备初始代码状态；
   - 有些任务需要缺失实现，有些任务需要带 bug 的实现；
   - 目标不是自然语言答案，而是能让测试通过的代码修改。

4. 合成 unit tests
   - 为每个任务生成可执行测试；
   - 测试用于判断 agent 是否真正解决任务；
   - 测试本身也是数据质量的关键。

5. Agent rollout
   - 让 coding agent 在环境中读文件、改代码、跑测试；
   - 记录完整轨迹，而不是只保留最终 patch；
   - 轨迹中包含观察、决策、工具调用、测试反馈和修复过程。

6. 执行验证与过滤
   - 只有测试通过、轨迹合理、任务和环境一致的样本才保留；
   - 失败或低质量样本被丢弃或用于后续分析。
```


### 1.2 SWE-Next: Scalable Real-World Software Engineering Tasks for Agents

论文：SWE-Next: Scalable Real-World Software Engineering Tasks for Agents  
链接：https://arxiv.org/abs/2603.20691

![SWE-Next end-to-end pipeline](assets/agentic_data_pipelines/figures/swe_next_pipeline_page2.png)

#### 要解决的问题

真实 PR 和 commit 很多，但不是每个 PR 都适合做 agent 训练数据。一个 PR 可能：

- 没有测试；
- 测试环境搭不起来；
- 修改范围太大，任务不可归因；
- merged 版本并没有带来明确的测试提升；
- base 和 merged 之间有不稳定依赖。

SWE-Next 关注的问题是：如何从真实 PR 中筛出 self-verifying SWE task。

#### 数据构造方案

核心流程：

```text
1. 收集真实 merged PR
   - 从大量 GitHub repo 中挖 merged PR；
   - 抽取 PR 对应的 base commit 和 merged commit。

2. 构造候选 commit pair
   - base commit: 修改前状态；
   - merged commit: 修改后状态；
   - PR 描述、commit message、diff 可用于生成任务描述。

3. 执行 base 版本测试
   - 在 base commit 上运行测试；
   - 记录失败/通过情况。

4. 执行 merged 版本测试
   - 在 merged commit 上运行同一组测试；
   - 检查是否出现严格测试提升。

5. 保留 self-verifying instances
   - merged 相比 base 有明确 improvement；
   - 没有引入 regression；
   - 环境可复现；
   - 任务可以由测试自动验证。

6. 收集 agent trajectories
   - agent 在 base commit 上尝试完成 PR 任务；
   - 轨迹必须 evidence-driven，不能只是 speculative patch。
```

系统层面，它还提出 repo-quarter profiles，用时间相近的 commit 复用环境配置，避免每个 commit pair 重新构建完整环境。


### 1.3 ScaleSWE: Immersion in the GitHub Universe

论文：Immersion in the GitHub Universe: Scaling Coding Agents to Mastery  
链接：https://arxiv.org/html/2602.09892v1

![ScaleSWE sandboxed multi-agent construction pipeline](assets/agentic_data_pipelines/figures/scaleswe_pipeline_page3.png)

#### 要解决的问题

大规模 SWE 数据构造的瓶颈不只是任务数量，而是多个环节都难自动化：

- 环境搭建难；
- 单元测试生成难；
- 问题描述从 PR/diff 还原难；
- 数据质量过滤难；
- agent 轨迹蒸馏成本高。

ScaleSWE 把数据构造拆成多个专门 agent，而不是让一个模型一次完成所有事情。

#### 数据构造方案

整体是 sandboxed multi-agent workflow：

```text
输入:
  大量 GitHub PRs

Agent 1: Environment Builder
  - 分析 repo 依赖和运行方式；
  - 构建 sandbox 环境；
  - 安装依赖；
  - 确认可执行。

Agent 2: Unit-test Creator
  - 根据 PR diff 和项目上下文生成测试；
  - 测试要能捕获 base 版本问题；
  - merged 或正确 patch 应该通过。

Agent 3: Problem Statement Writer
  - 从 PR title、body、diff、测试目标中合成问题描述；
  - 描述不能泄漏最终 patch；
  - 任务要足够明确，让 solver 可以尝试。

Solver / Distillation
  - 让 agent 在环境中解题；
  - 记录轨迹；
  - 筛选高质量 successful trajectories。

Quality Assurance
  - 执行测试；
  - 检查 patch 是否解决问题；
  - 过滤不可复现、测试不稳定、描述不一致的实例。
```

ScaleSWE 的核心启发是：数据构造本身可以是一个 agent system。每个 agent 只负责一个明确环节，质量控制在环节之间进行。


### 1.4 daVinci-Dev: Agent-native Mid-training for Software Engineering

论文：daVinci-Dev: Agent-native Mid-training for Software Engineering  
链接：https://arxiv.org/abs/2601.18418


![daVinci-Dev agent-native data generation pipeline](assets/agentic_data_pipelines/figures/davinci_dev_pipeline_page5.png)

#### 要解决的问题

传统代码模型训练数据多是静态代码或单轮 instruction-code。SWE agent 真实工作方式不同：

```text
理解需求 -> 搜索文件 -> 阅读上下文 -> 修改多处代码 -> 执行测试 -> 观察失败 -> 再修复
```

如果训练数据不保留这个动态信息流，模型就难学到 agentic development behavior。

#### 数据构造方案

论文提出 agent-native data，两类轨迹互补：

```text
1. Contextually-native trajectories
   - 保留 agent 看到的上下文；
   - 保留任务、观察、推理、决策、工具调用之间的信息流；
   - 优点是覆盖广、成本相对低；
   - 缺点是环境真实性可能较弱。

2. Environmentally-native trajectories
   - 从真实可执行 repo 中采集；
   - observation 来自真实工具调用、shell、测试执行；
   - 优点是交互真实、反馈可靠；
   - 缺点是构建和执行成本高。
```

#### 方法特点

训练目标可以分三种：

```text
1. Full trajectory SFT
   学完整 observe-act-test-repair 流程。

2. Next-action prediction
   给当前状态，让模型预测下一步该 inspect、edit、render 还是 test。

3. Failure repair training
   给失败测试和当前代码，让模型生成最小 patch。
```


### 1.5 daVinci-Env / OpenSWE: Open SWE Environment Synthesis at Scale

论文：daVinci-Env: Open SWE Environment Synthesis at Scale  
链接：https://arxiv.org/abs/2603.13023


![OpenSWE / daVinci-Env framework](assets/agentic_data_pipelines/figures/davinci_env_pipeline_page4.png)

#### 要解决的问题

SWE agent 训练需要大规模可执行环境，但开源数据集环境数量和 repo 多样性有限，工业级数据工厂又通常不透明。daVinci-Env / OpenSWE 的目标是开放地构建大规模 SWE agent environment。

#### 数据构造方案

它不是只构造 task，而是构造 executable environment：

```text
1. Repo collection
   - 收集大量 Python repos；
   - 覆盖不同项目、依赖、测试框架。

2. Multi-agent environment synthesis
   - Repo exploration agent: 理解 repo 结构、依赖、测试入口；
   - Dockerfile construction agent: 生成可构建 Dockerfile；
   - Evaluation script agent: 生成 eval 脚本；
   - Test analysis agent: 运行测试并分析失败原因。

3. Distributed construction
   - 在多节点集群上并行构建；
   - 保存 Dockerfile、eval scripts、环境 metadata。

4. Quality-centric filtering
   - 过滤不可执行环境；
   - 过滤太简单或无学习价值环境；
   - 过滤不可解或过难环境；
   - 保留 difficulty 合适的环境用于轨迹采样。

5. Trajectory sampling and curation
   - 在高质量环境上采样 agent 轨迹；
   - 用执行结果和难度信息筛选训练数据。
```

它把“环境”提升为训练资产。一个好环境可以派生多个任务、多条轨迹、多轮 RL 经验。


### 1.6 SWE-Master: Post-training Pipeline for SWE Agents

论文：SWE-Master: Unleashing the Potential of Software Engineering Agents via Post-Training  
链接：https://arxiv.org/html/2602.03411v1

![SWE-Master trajectory filtering and training pipeline](assets/agentic_data_pipelines/figures/swe_master_pipeline_page6.png)

#### 要解决的问题

SWE agent 的能力不是单靠 SFT 数据就能完全获得。需要：

- 高质量 teacher trajectories；
- 长程 SFT；
- 真实执行反馈 RL；
- 测试时多候选验证和选择；
- 更强的代码导航工具。

#### 数据构造和训练方案

SWE-Master 是一个端到端 post-training recipe：

```text
1. Teacher trajectory synthesis
   - 使用强 teacher agent 在 SWE 环境中解题；
   - 记录长程交互轨迹；
   - 轨迹包含文件搜索、阅读、编辑、测试、修复。

2. Data curation
   - 过滤失败轨迹；
   - 控制任务难度；
   - 清理过长、无效或 reward hacking 风险轨迹。

3. Long-horizon SFT
   - 训练模型模仿完整 agent 行为；
   - 不是只训练 final patch。

4. RL with real environments
   - 在真实环境中执行 agent action；
   - 用测试结果、任务完成度等作为 reward；
   - 加入防 reward hacking 约束。

5. Test-time scaling
   - 推理时生成多个候选解决方案；
   - 使用环境反馈或 verifier 排序；
   - 选择最可能通过的 patch。

6. Tool upgrade
   - 从 grep/search 升级到 LSP-based code navigation；
   - 提升定位和理解大型代码库的能力。
```

#### 方法特点

它说明 agent 训练不是单阶段数据问题，而是：

```text
数据构造 + 执行反馈 + RL + 推理时 verifier/rerank
```



### 1.7 SWE-Lego: SFT Recipe with Real + Synthetic Data

论文：SWE-Lego: Pushing the Limits of Supervised Fine-tuning for Software Issue Resolving  
链接：https://arxiv.org/abs/2601.01426

![SWE-Lego data construction pipeline](assets/agentic_data_pipelines/figures/swe_lego_pipeline_page3.png)

#### 要解决的问题

很多 SWE agent 系统依赖复杂 mid-training + SFT + RL。SWE-Lego 问的是：如果只做高质量 SFT，能推到什么程度？

#### 数据构造方案

它的核心是三块：

```text
1. SWE-Lego dataset
   - 32K 高质量 task instances；
   - 18K validated trajectories；
   - 混合真实数据和 synthetic data；
   - 真实数据提供自然分布；
   - synthetic data 补足数量和覆盖。

2. Validated trajectories
   - 轨迹必须能通过验证；
   - 不保留只看起来合理但不能执行成功的样本。

3. Difficulty curriculum
   - 按难度组织训练；
   - 先学更容易、更明确、更短路径任务；
   - 再学复杂、多文件、长程任务。

4. Error masking
   - 对训练中某些错误或噪声 token 做 mask；
   - 提升 action quality。

5. Test-time scaling with verifier
   - SFT 模型生成多个候选；
   - 用 verifier 提升最终成功率。
```

SWE-Lego 的重要启发是：高质量、可验证、带难度课程的 SFT 数据仍然非常有价值。不是所有提升都必须先上 RL。


### 1.8 Socratic-SWE: Self-Evolving Coding Agents via Trace-Derived Agent Skills

论文：Socratic-SWE: Self-Evolving Coding Agents via Trace-Derived Agent Skills  
链接：https://arxiv.org/abs/2606.07412

![Socratic-SWE closed-loop self-evolution pipeline](assets/agentic_data_pipelines/figures/socratic_swe_pipeline_page2.png)

#### 要解决的问题

传统 synthetic data 往往用固定 mutation 或 bug injection，数据分布与当前模型弱点无关。模型失败在哪里，下一轮数据却未必补哪里。

Socratic-SWE 的思路是让数据构造闭环自适应：

```text
模型失败 -> 从失败轨迹提炼技能/模式 -> 生成 targeted tasks -> 再训练 -> 再收集失败
```

#### 数据构造方案

详细流程：

```text
1. Solver rollout
   - 当前 agent 在 SWE 任务上解题；
   - 记录成功和失败轨迹；
   - 失败轨迹尤其重要。

2. Trace analysis
   - 分析 agent 在哪里失败；
   - 是定位错文件？
   - 是测试理解错？
   - 是 patch 太大？
   - 是修了表面但破坏其他逻辑？

3. Skill distillation
   - 从轨迹中提炼 structured agent skills；
   - skill 不是泛泛建议，而是可用于生成任务的结构化模式；
   - 包含 recurring failure 和 effective repair pattern。

4. Targeted repair task generation
   - 根据 skill 在真实 repo 中生成新任务；
   - 新任务专门攻击模型弱点。

5. Execution validation
   - 任务必须可执行、可验证；
   - 不可验证任务被过滤。

6. Solver-gradient alignment reward
   - 评估任务是否真的有助于当前 solver 改进；
   - 不是所有可验证任务都有训练价值。

7. Iterative update
   - 用新数据更新 solver；
   - 更新后继续 rollout；
   - 形成多轮自进化。
```

### 1.9 Hybrid-Gym: Training Coding Agents to Generalize Across Tasks

论文：Hybrid-Gym: Training Coding Agents to Generalize Across Tasks  
链接：https://arxiv.org/abs/2602.16819


![Hybrid-Gym intermediate skill decomposition](assets/agentic_data_pipelines/figures/hybrid_gym_pipeline_page2.png)

#### 要解决的问题

真实 coding agent 不只会 solve issue，还要：

- 探索代码库；
- 找相关函数；
- 理解依赖；
- 生成测试；
- 判断修改位置；
- 设计架构。

如果训练数据只有完整 issue solving，模型可能缺少可迁移的中间技能。

#### 数据构造方案

Hybrid-Gym 先分析复杂 agent 轨迹，把它们拆成更细粒度能力，再设计 scalable synthetic auxiliary tasks。

示例任务：

```text
Function localization:
  给一个 bug/需求描述，让 agent 找应该修改哪个函数。

Dependency search:
  给一个 symbol 或功能，让 agent 找依赖链。

Codebase exploration:
  让 agent 在 repo 中收集完成任务所需信息。
```

这些任务通常比完整 SWE task 短、更便宜、更容易验证，但训练出的能力能迁移到真实复杂任务。

#### 方法特点

它提供了一个很重要的判断：训练 agent 不一定只靠完整任务数据，中间技能数据可能更高性价比。


## 2. Search / Deep Research Agent 数据构造

### 2.1 SAGE: Steerable Agentic Data Generation for Deep Search with Execution Feedback

论文：SAGE: Steerable Agentic Data Generation for Deep Search with Execution Feedback  
链接：https://arxiv.org/abs/2601.18202

图：SAGE dual-agent data generation pipeline。

![SAGE dual-agent data generation pipeline](assets/agentic_data_pipelines/figures/sage_pipeline_page2.png)

#### 要解决的问题

Deep search 问题的人类标注很贵，因为一次完整搜索需要多轮检索、阅读、推理。直接让 LLM 生成 QA 又容易太简单、不可解或答案不可靠。

SAGE 的目标是生成 difficulty-controlled deep search data。

#### 数据构造方案

它让 generator 和 search agent 交互：

```text
1. Data generator 提出候选 QA
   - 基于语料生成问题和答案；
   - 问题有目标难度。

2. Search agent 尝试解决问题
   - 真正执行搜索；
   - 收集检索路径、失败原因、证据不足点。

3. Execution feedback
   - 如果问题太简单，要求 generator 增加多跳、比较、约束；
   - 如果问题不可解，要求补充 grounding 或改问题；
   - 如果答案不唯一，要求收窄条件。

4. 多轮 refine
   - 直到问题达到目标难度；
   - 同时保持可解和答案正确。

5. 训练 deep search agent
   - 用最终 QA 和搜索轨迹训练；
   - 提升 deep search benchmark 表现。
```

#### 方法特点

难度不是人工拍脑袋，也不是用问题长度估计，而是由 agent 实际执行反馈决定。


### 2.2 QUEST: Rubric-tree Synthetic Deep Research Tasks

论文：QUEST: Training Frontier Deep Research Agents with Fully Synthetic Tasks  
链接：https://arxiv.org/abs/2605.24218

图：QUEST rubric-tree data synthesis pipeline。

![QUEST rubric-tree data synthesis pipeline](assets/agentic_data_pipelines/figures/quest_pipeline_page4.png)

#### 要解决的问题

Deep research agent 需要覆盖事实查找、引用 grounding、报告合成、长程搜索等多能力。人工标注昂贵，普通 synthetic QA 又很难保证能力覆盖和可验证 reward。

QUEST 的关键是：先设计 unified rubric trees，再沿树生成任务和 rewards。

#### 数据构造方案

流程：

```text
1. 定义 rubric tree
   - 把 deep research 能力拆成树状评价项；
   - 每个叶子节点对应可检查能力或约束。

2. 沿 rubric 采样任务
   - 任务不是随便生成；
   - 每个任务明确覆盖哪些能力节点。

3. 合成可验证 reward
   - 根据 rubric 生成检查标准；
   - 尽量避免纯人工标注。

4. 训练 recipe
   - mid-training；
   - SFT；
   - RL；
   - context management。
```

#### 方法特点

rubric tree 让 synthetic data 不再是散点采样，而是按能力结构系统覆盖。


### 2.3 S1-DeepResearch: Graph-grounded Task + Trajectory Verification

论文：S1-DeepResearch: Beyond Search, Toward Real-World Long-Horizon Research Agents  
链接：https://arxiv.org/abs/2606.15367

图：S1-DeepResearch agentic data synthesis framework。

![S1-DeepResearch agentic data synthesis framework](assets/agentic_data_pipelines/figures/s1_deepresearch_pipeline_page5.png)

#### 要解决的问题

很多 deep research 数据仍然偏 closed-ended QA 和信息定位，不能覆盖真实研究任务所需的规划、证据整合、报告写作、文件理解、技能使用。

#### 数据构造方案

S1-DeepResearch 使用统一轨迹构造范式：

```text
1. Graph-grounded task formulation
   - 先构造或利用图结构 grounding；
   - 图中节点/边表达实体、证据、文件、关系或任务依赖。

2. Agentic trajectory rollout
   - agent 按任务执行长程搜索、阅读、综合、写作；
   - 轨迹覆盖信息获取和知识合成。

3. Multi-dimensional trajectory verification
   - 不只检查答案；
   - 同时检查推理、引用、报告结构、文件理解、技能使用等。
```

#### 方法特点

它把复杂任务建立在结构图上，而不是只靠一段自然语言 prompt。


### 2.4 AgentIR: Reasoning-Aware Retrieval for Deep Research Agents

论文：AgentIR: Reasoning-Aware Retrieval for Deep Research Agents  
链接：https://arxiv.org/abs/2603.04384

图：AgentIR / DR-Synth reranking pipeline。

![AgentIR / DR-Synth reranking pipeline](assets/agentic_data_pipelines/figures/agentir_pipeline_page4.png)

#### 要解决的问题

Deep research agent 在搜索前通常会生成 reasoning trace，但传统 retriever 只看 query，忽略了 agent 当前推理中的丰富意图。

#### 数据构造方案

AgentIR 做两件事：

```text
1. Reasoning-Aware Retrieval
   - retriever 输入不只是 search query；
   - 同时包含 agent 当前 reasoning trace；
   - 联合编码后检索更匹配当前子目标的文档。

2. DR-Synth
   - 从标准 QA 数据集合成 deep research retriever training data；
   - 构造 reasoning trace + query + relevant document 的训练样本。
```

#### 方法特点

它把 agent 的中间思考作为检索信号。对长程任务来说，检索目标经常依赖当前推理阶段。


### 2.5 WebClipper: Graph-based Trajectory Pruning

论文：WebClipper: Efficient Evolution of Web Agents with Graph-based Trajectory Pruning  
链接：https://arxiv.org/html/2602.12852v1

图：WebClipper trajectory pruning pipeline。

![WebClipper trajectory pruning pipeline](assets/agentic_data_pipelines/figures/webclipper_pipeline_page3.png)

#### 要解决的问题

Web/deep research agent 轨迹很长，常见问题是：

- 重复搜索；
- 循环推理；
- 探索无效分支；
- 工具调用过多；
- thought 和保留动作不连贯。

直接拿这些轨迹训练会让学生模型学到低效行为。

#### 数据构造方案

WebClipper 的流程：

```text
1. 收集原始轨迹
   - 从已有 web agent 蒸馏 ReAct-style 轨迹；
   - 轨迹包含 observation、thought、action。

2. 过滤初始轨迹
   - 去掉错误答案或明显失败样本。

3. Trajectory -> State Graph
   - 把 agent action 和 environment observation 抽象成图节点；
   - 边表示信息依赖或状态转移。

4. MNDAG pruning
   - 寻找从 query 到 final answer 的 minimum necessary DAG；
   - 删除循环、重复搜索、无效分支。

5. Coherence-aware thought rewriting
   - 删除动作后，原 thought 可能不连贯；
   - 重写保留步骤的 reasoning，使轨迹可训练。

6. Agent evolution
   - 用剪枝后的轨迹继续训练；
   - 提升效率同时保持或提升准确率。
```

#### 方法特点

它不是简单截短轨迹，而是基于状态图保留必要信息链。


## 3. Web / GUI / Computer-use Agent 数据构造

### 3.1 SynthAgent: Adapting Web Agents with Synthetic Supervision

论文：SynthAgent: Adapting Web Agents with Synthetic Supervision  
链接：https://arxiv.org/html/2511.06101v3

图：SynthAgent synthetic supervision framework。

![SynthAgent synthetic supervision framework](assets/agentic_data_pipelines/figures/synthagent_pipeline_page3.png)

#### 要解决的问题

给新网站适配 web agent 时，环境特定任务和 demonstrations 很少。直接合成任务会遇到两个质量问题：

```text
1. Task hallucination
   任务说要点击某按钮，但网页上根本没有这个按钮。

2. Noisy trajectory
   轨迹有冗余动作、无效动作、和任务不匹配的动作。
```

#### 数据构造方案

SynthAgent 有四个阶段：

```text
1. Task Synthesis
   - 对目标网站进行 categorized exploration；
   - 探索不同类别网页元素；
   - 基于真实元素和 affordance 合成任务。

2. Task Refinement
   - 在 trajectory collection 过程中检查任务和 observation 是否冲突；
   - 如果任务要求的元素不存在或状态不一致，则 refine task；
   - 只在发现冲突时修改任务，避免过度改写。

3. Trajectory Collection
   - web agent 在网站中执行任务；
   - 记录 observation/action。

4. Trajectory Refinement
   - 用全局上下文检查轨迹；
   - 删除冗余动作；
   - 修正 misaligned actions；
   - 提升 demonstration 质量。

5. Fine-tuning
   - 用 refined synthetic data 适配开源 web agent。
```

#### 方法特点

它把 synthetic supervision 的质量控制拆成 task-level 和 trajectory-level 两层。


### 3.2 AutoPlay: Scaling Synthetic Task Generation via Exploration

论文：Scaling Synthetic Task Generation for Agents via Exploration  
链接：https://arxiv.org/abs/2509.25047

图：AutoPlay exploration-grounded task generation pipeline。

![AutoPlay exploration-grounded task generation pipeline](assets/agentic_data_pipelines/figures/autoplay_pipeline_page2.png)

#### 要解决的问题

许多 synthetic task 是 LLM 凭空生成的，缺少环境 grounding，导致：

- 覆盖不足；
- 任务不可执行；
- 任务不可验证；
- 没发现环境里真正有价值的状态和功能。

AutoPlay 的核心是：先探索环境，再生成任务。

#### 数据构造方案

流程：

```text
1. Exploration phase
   - MLLM explorer agent 进入 Android/Ubuntu 环境；
   - 系统性探索按钮、菜单、页面、状态变化；
   - 保存探索轨迹和发现的功能。

2. Task generation phase
   - task generator 使用探索轨迹作为上下文；
   - 结合 task guideline prompts 生成任务；
   - 任务必须 diverse、executable、verifiable。

3. Demonstration synthesis
   - MLLM task executor 尝试完成任务；
   - verifier 检查任务完成情况；
   - 成功 trajectory 入库。

4. Training and RL
   - 用生成任务和 demonstrations 训练 UI agent；
   - verifier reward 也可用于 RL。
```

#### 方法特点

任务来自环境 affordance，而不是来自模型想象。


### 3.3 AgentSynth: Scalable Task Generation for Generalist Computer-Use Agents

论文：AgentSynth: Scalable Task Generation for Generalist Computer-Use Agents  
链接：https://arxiv.org/abs/2506.14205

图：AgentSynth task generation pipeline。

![AgentSynth task generation pipeline](assets/agentic_data_pipelines/figures/agentsynth_pipeline_page3.png)

#### 要解决的问题

长程 computer-use tasks 难生成、难标注、成本高。如果直接让 LLM 生成复杂任务，常常不可执行或难度不可控。

AgentSynth 利用 information asymmetry：子任务生成容易，但组合后对 agent 来说很难。

#### 数据构造方案

```text
1. Persona-guided task proposer
   - 根据 persona 和场景生成子任务；
   - 子任务简单、明确、可执行。

2. Subtask execution
   - execution agent 完成每个子任务；
   - 记录轨迹和状态变化。

3. Composite task construction
   - 把多个子任务组合成一个长程任务；
   - 组合后的任务需要跨多个步骤完成。

4. Difficulty control
   - 通过子任务数量控制难度；
   - level 越高，包含子任务越多。

5. Low-cost trajectory generation
   - 自动生成并验证 trajectories；
   - 成本远低于人工标注。
```

#### 方法特点

复杂任务不是一次生成，而是由可验证子任务组合。


### 3.4 GUI-ReWalk: Stochastic Exploration and Intent-Aware Reasoning

论文：GUI-ReWalk: Massive Data Generation for GUI Agent via Stochastic Exploration and Intent-Aware Reasoning  
链接：https://arxiv.org/abs/2509.15738

图：GUI-ReWalk framework overview。

![GUI-ReWalk framework overview](assets/agentic_data_pipelines/figures/gui_rewalk_pipeline_page5.png)

#### 要解决的问题

GUI agent 需要真实、多样的交互轨迹。人工标注贵，直接合成轨迹又容易缺少真实探索行为。

GUI-ReWalk 的做法是先随机探索，再推断目标。

#### 数据构造方案

```text
1. Stochastic exploration
   - agent 像人类试错一样随机/半随机操作 GUI；
   - 记录状态变化和交互路径；
   - 增加轨迹多样性。

2. Reasoning-guided phase
   - 分析探索轨迹；
   - 推断这条轨迹可以对应什么用户目标；
   - 把无目的探索转成有目标 demonstration。

3. Multi-stride task generation
   - 支持跨多个 app 或多个阶段的长程工作流；
   - 构造更长、更真实的 GUI tasks。

4. Training
   - 用生成轨迹训练 GUI agent；
   - 提升轨迹多样性和真实 intent 覆盖。
```

#### 方法特点

它是 trajectory-first synthesis：先产生有效状态变化，再反推用户意图。


### 3.5 WebSynthesis: World Model-Guided MCTS for WebAgent Trajectory Synthesis

论文：WebSynthesis: World Model-Guided Monte Carlo Tree Search for Efficient WebAgent Trajectory Synthesis  
链接：https://openreview.net/forum?id=moOUJXscIz

图：WebSynthesis world-model-guided MCTS pipeline。

![WebSynthesis world-model-guided MCTS pipeline](assets/agentic_data_pipelines/figures/web_synthesis_pipeline_page4.png)

#### 要解决的问题

真实网站交互成本高，且存在：

- 网络不稳定；
- 网站访问限制；
- 状态不可逆；
- 搜索空间难做树搜索；
- 大规模采集轨迹成本高。

WebSynthesis 用 world model 模拟网页状态转移。

#### 数据构造方案

```text
1. 训练/调用 LLM-based World Model
   - 输入当前网页状态和 agent action；
   - 输出模拟的下一网页状态；
   - 减少对真实网络环境依赖。

2. Monte Carlo Tree Search
   - 在模拟状态空间中做可逆探索；
   - 尝试不同 action 分支；
   - 找到更优轨迹。

3. Trajectory synthesis
   - 用 world model + MCTS 合成大量 interaction trajectories；
   - 轨迹不依赖真实网站每一步执行。

4. Agent training
   - 用合成轨迹训练 web agent；
   - 实验显示纯 synthetic trajectories 也能有强表现。
```

#### 方法特点

它把真实 web environment 替换成可控模拟器，解决规模和不可逆状态问题。


### 3.6 DynaWeb: Model-Based Reinforcement Learning of Web Agents

论文：DynaWeb: Model-Based Reinforcement Learning of Web Agents  
链接：https://arxiv.org/html/2601.22149v1

图：DynaWeb model-based RL pipeline。

![DynaWeb model-based RL pipeline](assets/agentic_data_pipelines/figures/dynaweb_pipeline_page2.png)

#### 要解决的问题

Web agent 在线 RL 难点：

- 真实互联网交互慢；
- 成本高；
- 有风险，比如误提交、误购买；
- 状态随机且不可控；
- on-policy experience 难扩展。

DynaWeb 用 web world model 作为 synthetic environment，让 agent 通过 dreaming rollout 学习。

#### 数据构造和训练方案

```text
1. Web world model
   - 输入当前页面表示和 agent action；
   - 预测下一页面表示；
   - 模拟 web server / environment。

2. Dream rollouts
   - policy agent 在 world model 中生成大量 on-policy trajectories；
   - 不需要每一步访问真实网站。

3. Expert trajectory interleaving
   - 将真实 expert trajectories 随机混入 on-policy rollouts；
   - 提升训练稳定性和 sample efficiency。

4. Model-based RL
   - imagined rollouts 直接用于策略优化；
   - world model 从辅助工具变成训练环境。
```

#### 方法特点

它强调 imagined rollouts 是一等训练经验，不只是 SFT 数据补充。


### 3.7 Agent-as-Annotators: Structured Distillation of Web Agent Capabilities

论文：Structured Distillation of Web Agent Capabilities Enables Generalization  
链接：https://arxiv.org/abs/2604.07776

图：Agent-as-Annotators pipeline。

![Agent-as-Annotators pipeline](assets/agentic_data_pipelines/figures/agent_as_annotators_pipeline_page2.png)

#### 要解决的问题

强 frontier LLM 能操作复杂网站，但成本高、依赖 API，不适合本地部署。目标是用一个 frontier teacher 结构化生成 trajectories，蒸馏到小模型。

#### 数据构造方案

它把合成轨迹生成类比成人类标注流程：

```text
1. Task Designer
   - 设计任务；
   - 确保任务和环境相关。

2. Annotator
   - 执行任务；
   - 生成轨迹；
   - 记录 reasoning traces。

3. Supervisor / Judge
   - 检查轨迹质量；
   - 过滤失败或低质量样本；
   - 提供 evaluation hints。

4. Fine-tuning
   - 用过滤后的 teacher trajectories 训练 student agent。
```

论文中用 Gemini 3 Pro 生成 3,000 条轨迹，过滤到 2,322 条，再训练 9B student。

#### 方法特点

不是一个 teacher 一次性输出所有东西，而是结构化成多个标注角色。


## 4. Tool-use / Function-calling Agent 数据构造

### 4.1 APIGen-MT: Blueprint-to-Dialogue Multi-turn Data Generation

论文：APIGen-MT: Agentic Pipeline for Multi-Turn Data Generation via Simulated Agent-Human Interplay  
链接：https://arxiv.org/abs/2504.03601

图：APIGen-MT blueprint-to-dialogue framework。

![APIGen-MT blueprint-to-dialogue framework](assets/agentic_data_pipelines/figures/apigen_mt_pipeline_page4.png)

#### 要解决的问题

多轮 function-calling 数据需要真实的人机动态，但人工收集贵。直接生成完整对话又容易前后不一致、工具调用错误。

APIGen-MT 的关键是先生成 blueprint，再转对话。

#### 数据构造方案

```text
Phase 1: Blueprint generation
  - 生成详细 task blueprint；
  - 包含用户目标、约束、ground-truth actions；
  - LLM reviewer committee 多轮审查；
  - 通过 iterative feedback 修正 blueprint。

Phase 2: Dialogue generation
  - 将 blueprint 转成完整 multi-turn agent-human interaction；
  - 模拟用户逐步提供信息；
  - agent 执行 function calls；
  - 保证轨迹和 ground-truth actions 一致。

Training
  - 用生成的 multi-turn trajectories 训练 function-calling model。
```

#### 方法特点

blueprint 是中间结构，它让自然语言对话和可验证 action 之间有桥梁。


### 4.2 ASTRA: Tool-call Graph Topology and Verifiable Reinforcement Arenas

论文：ASTRA: Automated Synthesis of agentic Trajectories and Reinforcement Arenas  
链接：https://arxiv.org/html/2601.21558v1

图：ASTRA tool-chain trajectory synthesis pipeline。

![ASTRA tool-chain trajectory synthesis pipeline](assets/agentic_data_pipelines/figures/astra_pipeline_page3.png)

#### 要解决的问题

Tool-use agent 训练面临：

- 手工数据成本高；
- LLM 模拟环境不可验证；
- SFT-only 缺少在线反馈；
- RL-only 初始策略弱；
- 多轮长程学习不稳定。

ASTRA 用两套互补机制：trajectory synthesis for SFT 和 verifiable environment synthesis for RL。

#### 数据构造方案

```text
1. Tool document collection and filtering
   - 收集工具 schema；
   - 标准化 schema；
   - 按工具能力分组和过滤。

2. Tool-chain construction
   - 构建工具调用 transition graph；
   - 在 graph 上 walk 得到候选 tool chains；
   - 验证工具间依赖是否成立。

3. Task construction and scoring
   - 根据 tool chain 生成任务；
   - 加入 consistency constraints；
   - 评分并过滤低质量任务。

4. Multi-turn trajectory collection
   - agent 与工具/模拟器交互；
   - 生成多轮轨迹。

5. Verifiable environment synthesis
   - 将 QA trace 分解成语义拓扑；
   - 生成 code-executable, rule-verifiable environments；
   - 支持 deterministic rewards。

6. Training
   - SFT 学 broad tool-use competence；
   - online RL 在 verifiable environments 中提升长程能力；
   - trajectory-level reward 同时考虑完成度和效率。
```

#### 方法特点

它把工具调用流程拓扑化，避免随机多轮；又把 RL 环境做成规则可验证，避免 LLM judge 不稳定。


### 4.3 StateGen: State-Grounded Multi-Agent Synthetic Data Generation

论文：State-Grounded Multi-Agent Synthetic Data Generation for Tool-Augmented LLMs  
链接：https://arxiv.org/abs/2606.16307

图：StateGen four-role architecture。

![StateGen four-role architecture](assets/agentic_data_pipelines/figures/stategen_pipeline_page3.png)

#### 要解决的问题

多轮 tool-use 数据常见问题是状态幻觉。用户上一轮改了某字段，下一轮又引用“那个”，如果没有权威状态，模拟器和 agent 很容易不一致。

StateGen 的核心是 authoritative state manager。

#### 数据构造方案

四角色循环：

```text
1. Persona-conditioned user simulator
   - 根据 persona 生成多轮用户需求；
   - persona 包含偏好、表达风格、约束等。

2. Agent under test
   - 尝试理解用户并调用工具；
   - 可能追问、执行、修改状态。

3. State-grounded tool simulator
   - 工具返回不由 LLM 随意编；
   - 由 authoritative state object 决定；
   - backend-is-truth。

4. Multi-axis judge
   - 从多个维度评分；
   - 包括任务完成、工具调用、幻觉、对话质量等。
```

关键设计：

```text
authoritative state manager:
  - 维护结构化 world-state；
  - 每次工具调用更新状态；
  - 所有 agent 看到的工具反馈都来自该状态；
  - 支持把 sub-agent 声明成工具，共享同一状态。
```

#### 方法特点

它用状态对象从机制上减少 hallucination，而不是事后让 judge 判断。


### 4.4 Trajectory2Task: From Valid Trajectories to Complex User Intents

论文：Trajectory2Task: Training Robust Tool-Calling Agents with Synthesized Yet Verifiable Data for Complex User Intents  
链接：https://arxiv.org/abs/2601.20144

图：Trajectory2Task trajectory-first synthesis pipeline。

![Trajectory2Task trajectory-first synthesis pipeline](assets/agentic_data_pipelines/figures/trajectory2task_pipeline_page5.png)

#### 要解决的问题

真实用户请求常常不是固定、明确、可行的：

- ambiguous intent；
- changing intent；
- infeasible intent；
- 中途改需求；
- 需要 agent 澄清。

传统 tool-calling 数据多是理想化、固定、清晰任务。

#### 数据构造方案

Trajectory2Task 反过来做：

```text
1. Multi-turn exploration
   - 先生成有效 tool-call trajectories；
   - 确保轨迹可执行、状态变化有效。

2. Trajectory -> task
   - 将有效轨迹转换成用户可见任务；
   - 用户任务不一定完全明确。

3. Controlled intent adaptations
   - ambiguous intent: 用户表达模糊，需要澄清；
   - changing intent: 用户中途改变需求；
   - infeasible intent: 用户需求违反约束，需要拒绝或解释。

4. Closed-loop evaluation and training
   - 因为底层轨迹有效，所以任务可验证；
   - 用 successful rollouts 微调模型。
```

#### 方法特点

它把“复杂用户意图”建立在有效轨迹上，避免先生成模糊任务导致不可验证。


### 4.5 GenesisFunc: Multi-Agent Data Generation for Function Calling

论文：GenesisFunc: Multi-Agent Data Generation for Accurate and Generalizable Function-Calling  
链接：https://arxiv.org/html/2605.28835v1

图：GenesisFunc overall framework。

![GenesisFunc overall framework](assets/agentic_data_pipelines/figures/genesisfunc_pipeline_page4.png)

#### 要解决的问题

Function-calling 数据要求高质量、多样性、场景覆盖和工具可靠性。已有 synthetic pipeline 常见问题：

- API 不可靠；
- 工具扩展困难；
- 对话场景单一；
- 多轮和多任务覆盖不足；
- 质量控制弱。

#### 数据构造方案

GenesisFunc 是三阶段：

```text
1. Tool Pool
   - 从可靠 benchmark 中选取 seed APIs；
   - 保证工具可用、schema 清晰；
   - 支持扩展到更多 downstream tools。

2. Multi-Agent Dialogue Generation
   - 多 agent 协同生成对话；
   - 通过角色区分、历史感知、参数槽位选择增加多样性；
   - agent-based scoring 控制质量。

3. Multi-Stage Evaluation
   - rule-based checks；
   - model-based checks；
   - targeted human review；
   - 检查格式、参数、执行正确性和对话质量。
```

#### 方法特点

它强调可靠工具池 + 多 agent 生成 + 多阶段评估。数据质量不是一个 judge 解决，而是多层控制。


### 4.6 RandomWorld: Procedural Environment Generation for Tool-Use Agents

论文：Procedural Environment Generation for Tool-Use Agents  
链接：https://arxiv.org/html/2506.11045v1

图：RandomWorld procedural environment generation pipeline。

![RandomWorld procedural environment generation pipeline](assets/agentic_data_pipelines/figures/randomworld_pipeline_page2.png)

#### 要解决的问题

很多 tool-use 数据的工具不可调用，或者任务只是单步调用，无法用于真正的交互式 SFT/RL。RandomWorld 的目标是程序化生成无限量可交互工具环境。

#### 数据构造方案

```text
1. Synthetic tool generation
   - 生成可调用 synthetic tools；
   - 工具有类型签名和返回值。

2. Fine-grained type hierarchy
   - 用类型系统保证工具之间可以组合；
   - 工具输出可以作为另一个工具输入。

3. Non-linear DAG trajectory skeletons
   - 从工具签名构造非线性 tool-call DAG；
   - 表示复杂任务的调用结构。

4. Environment construction
   每个环境包含：
   - tools；
   - goal state；
   - instruction；
   - 可交互中间输出。

5. Training
   - 支持 SFT；
   - 也支持 online RL，因为工具真实可调用。
```

#### 方法特点

它是程序化环境生成，而不是程序化 prompt 生成。


### 4.7 CoVe: Constraint-Guided Verification

论文：CoVe: Training Interactive Tool-Use Agents via Constraint-Guided Verification  
链接：https://arxiv.org/html/2603.01940v1

图：CoVe constraint-verification framework。

![CoVe constraint-verification framework](assets/agentic_data_pipelines/figures/cove_pipeline_page4.png)

#### 要解决的问题

多轮交互任务中，用户需求复杂、隐含、模糊，而工具执行需要确定参数。LLM 生成和 LLM judge 很难保证任务可解与轨迹正确。

CoVe 的核心是从显式约束开始。

#### 数据构造方案

```text
1. Sample explicit task constraints
   - 先采样确定目标；
   - 例如出发城市、酒店等级、退货商品、地址更新。

2. Constraint fuzzification
   - 把确定约束转成真实用户的模糊表达；
   - 例如不用 order id，而用“那件蓝色衬衫的订单”。

3. User simulator interaction
   - 用户模拟器按模糊表达多轮提供信息；
   - agent 需要澄清和调用工具。

4. Deterministic verification
   - 原始显式约束作为 checklist；
   - 检查工具调用是否满足所有约束；
   - 不依赖 LLM judge 判断正确性。

5. SFT and RL
   - SFT: teacher 生成轨迹，只保留 fully correct；
   - RL: deterministic verifier 提供 reward。
```

#### 方法特点

任务来自显式约束，所以天然可解；验证来自约束 checklist，所以更可靠。

## 5. WebCoding 可借鉴方案汇总

本节只整理可以迁移到 WebCoding_Data 的方案。前面论文介绍部分只保留各论文自身的数据构造方法；这里统一说明“怎么借鉴、借鉴自哪篇论文、可以落成什么数据管线”。

### 5.1 Environment-first：先造可执行前端环境，再从环境派生任务

参考来源：SWE-Playground；daVinci-Env / OpenSWE；RandomWorld。

核心思想是不要只构造 `instruction -> final code`，而是先构造一个 agent 可以进入、修改、运行、验证的前端任务环境。对 WebCoding 来说，一个环境至少应包含：初始项目、assets、本地启动方式、任务描述、测试脚本、渲染配置、验证结果和可选 agent 轨迹。

建议落地结构：

```text
web_env_id/
  initial/
    index.html
    styles.css
    script.js
    assets/
  target/
    index.html
    styles.css
    script.js
    assets/
  tests/
    interaction.spec.ts
    responsive.spec.ts
    visual_check.json
  task.json
  render_config.json
  verification.json
  trajectory.jsonl
```

构造流程：

```text
1. 合成或整理一个 mini frontend project。
2. 本地化所有 assets，禁止依赖远程 URL。
3. 识别页面组件、交互、响应式断点、资源依赖。
4. 派生 generate / edit / repair / refactor / test-generation 任务。
5. 为每个任务生成 Playwright、DOM、视觉、响应式验证器。
6. 让 solver agent 在 initial 项目上完成任务并记录轨迹。
7. 只保留 initial fail、target/solution pass、无 console error、无资源缺失的样本。
```

这条线适合作为 WebCoding_Data 的主干：先建设环境池，再从每个环境派生多条任务，而不是每条数据都从孤立 HTML 反推。

### 5.2 Diff/Test-first Edit Synthesis：用 A/B 页面版本构造 edit 数据

参考来源：SWE-Next。

SWE-Next 的关键是从真实 merged PR 中找 base/merged commit pair，并通过测试确认 merged 相比 base 有严格改进。迁移到 WebCoding，可以把 `commit pair` 换成 `页面版本 A / 页面版本 B`。

具体流程：

```text
1. 准备页面 A 和页面 B。
   - A 是修改前页面；
   - B 是目标页面；
   - A/B 可以来自真实网页迭代、模板演化、agent 修改轨迹或人工构造变体。

2. 计算多维 diff。
   - DOM diff: 节点、文本、属性变化；
   - CSS diff: selector、属性、media query 变化；
   - JS diff: handler、状态、DOM 更新逻辑变化；
   - screenshot diff: 目标区域视觉变化；
   - behavior diff: 点击、过滤、表单、modal、tab 等行为变化。

3. 由 diff 生成 edit instruction。
   - 明确目标区域；
   - 明确保留区域；
   - 不描述 B 中不存在的变化；
   - 不给出具体实现代码。

4. 生成 verifier。
   - A 应该在目标测试上失败；
   - B 应该通过；
   - 非目标区域 crop similarity 达标；
   - 移动端无横向滚动；
   - 无 console/network error。
```

这能比随机删除组件更自然地构造 edit/revision 数据，尤其适合训练“在已有页面上做局部修改并保持其他区域不变”的能力。

### 5.3 Multi-agent Web Coding Data Factory：把数据构造拆给多个 agent

参考来源：ScaleSWE；Agent-as-Annotators；GenesisFunc。

这些工作共同说明，大规模数据构造不要依赖一个 LLM 一次性输出所有东西，而应该拆成多个角色，各自负责一个可检查环节。

WebCoding 可以设计如下数据工厂：

```text
Env Agent:
  标准化前端项目结构，本地化 assets，确认可以通过 http.server 渲染。

Task Agent:
  根据页面结构和 rubric 生成 generate/edit/repair/refactor 任务。

Bug Agent:
  对 repair 类任务注入 taxonomy-driven bug，例如 responsive overflow、modal close failure、wrong selector。

Test Agent:
  生成 Playwright、DOM checker、responsive checker、visual crop spec。

Solver Agent:
  在 initial 项目里修改 HTML/CSS/JS，运行浏览器和测试，记录轨迹。

Visual/Judge Agent:
  查看截图和测试结果，判断视觉、交互、响应式、资源、accessibility 是否合格。

Curator Agent:
  统一 metadata，删除噪声轨迹，标注难度、失败标签、rubric 节点。
```

这条线适合支撑 70K 数据集生产，因为每个环节都有独立输出和过滤条件，方便并行化和定位质量问题。

### 5.4 Trajectory-native：保存完整前端开发轨迹，而不是只保存最终答案

参考来源：daVinci-Dev；SWE-Master；SWE-Lego。

WebCoding agent 真正需要学习的是：读文件、定位问题、修改代码、渲染页面、观察失败、继续修复、最终验证。训练数据如果只保留 final HTML，会丢掉最重要的 agent 行为。

建议保存的轨迹格式：

```json
{
  "task": "Fix mobile overflow in the pricing cards while preserving desktop layout.",
  "steps": [
    {"type": "inspect", "files": ["index.html", "styles.css"]},
    {"type": "edit", "file": "styles.css", "summary": "Add mobile media query for pricing grid."},
    {"type": "render", "viewport": "390x844", "observation": "Horizontal scroll remains."},
    {"type": "edit", "file": "styles.css", "summary": "Remove parent min-width and constrain cards."},
    {"type": "test", "result": "passed", "checks": ["no_horizontal_scroll", "desktop_preserved"]}
  ]
}
```

可以形成三类训练目标：

```text
1. Full trajectory SFT:
   学完整 inspect-edit-render-test-repair 流程。

2. Next-action prediction:
   给当前页面状态和测试结果，预测下一步应 inspect、edit、render 还是 test。

3. Failure repair:
   给失败测试、当前代码、截图观察，生成最小修复 patch。
```

### 5.5 SFT-only 强基线与难度课程

参考来源：SWE-Lego；SWE-Master。

在上 RL 之前，可以先做高质量 SFT 数据。关键不在堆量，而在 validated trajectory、error masking 和 curriculum。

建议课程：

```text
Level 1: 单文件静态页面生成。
Level 2: HTML + CSS 多文件修改。
Level 3: JS 交互修复，例如 tab/modal/filter/form。
Level 4: 响应式 + edit preservation。
Level 5: 多轮需求变更 + 模糊指代。
Level 6: 视觉高保真 + 交互 + accessibility + no external resource 综合任务。
```

过滤策略：

```text
- 不训练失败最终答案；
- 对无效 patch、重复 render、无关观察做 mask 或删除；
- 保留关键失败观察和有效修复动作；
- 每条轨迹必须可浏览器复现。
```

### 5.6 Failure-adaptive Data Flywheel：用模型真实失败决定下一轮造什么数据

参考来源：Socratic-SWE；SAGE。

这条线最适合“刷榜数据飞轮”。不要预设所有数据比例，而是让 baseline model 先跑 WebCompass、Design2Code、Vision2Web、FLAME-VLM-Code 风格任务，再根据失败分布定向造数据。

闭环流程：

```text
1. 当前模型跑一批 benchmark-like 或 synthetic tasks。
2. 保存输出代码、截图、Playwright 日志、console error、视觉分数。
3. 自动归因 failure tags。
4. 从失败轨迹中提炼 recurring failure pattern。
5. 针对高频失败生成 targeted data。
6. 浏览器验证并入库。
7. 重新训练后再评估，进入下一轮。
```

推荐 failure tags：

```text
visual_mismatch
layout_spacing_error
typography_error
color_error
interaction_failure
js_runtime_error
responsive_overflow
mobile_layout_collapse
edit_preservation_failure
missing_asset
external_resource_dependency
accessibility_failure
code_not_executable
```

示例：如果模型经常 mobile overflow，就合成 card grid、table、sidebar、pricing section、image gallery 的 overflow repair 任务；如果经常 JS interaction failure，就合成 tabs、modal、dropdown、filter、form validation 修复任务。

### 5.7 Hybrid-WebGym：构造前端中间技能数据

参考来源：Hybrid-Gym；AgentIR。

复杂 WebCoding 任务可以拆成一组可验证的中间技能。中间技能数据通常短、便宜、容易验证，但能明显增强复杂任务中的定位和诊断能力。

建议任务族：

```text
DOM localization:
  给 bug 描述和 HTML，输出应该修改的 DOM 节点或 selector。

CSS rule localization:
  给截图问题和 CSS，输出相关 selector、属性、media query。

JS event reasoning:
  给 HTML + JS + 失败交互描述，判断 handler 失效原因。

Responsive diagnosis:
  给 mobile/desktop 截图和 CSS，判断 overflow 或布局崩坏来源。

Visual diff explanation:
  给 before/after 截图或 diff，生成自然语言 edit instruction。

Playwright test generation:
  根据任务需求生成可执行测试，并要求 initial fail、target pass。

Asset dependency cleanup:
  找出外链、坏图、空 font-face、不可本地复现资源。

Edit preservation judgment:
  判断修改是否破坏非目标区域。
```

AgentIR 的 reasoning-aware retrieval 还可以迁移成“前端定位器”：输入用户需求和当前 agent 推理，输出相关文件、组件、CSS selector、JS function。

### 5.8 Difficulty-controlled Synthesis：用执行反馈控制任务难度

参考来源：SAGE。

WebCoding 任务难度不应只由 prompt 长度决定，而应由 agent 实际执行反馈决定。

可执行流程：

```text
1. 生成候选任务。
2. Solver agent 尝试实现。
3. 记录是否一次通过、几轮修复、失败类型、测试稳定性。
4. 如果太简单，增加约束：多 viewport、preservation、交互、accessibility。
5. 如果不可解，降低范围或补充 grounding。
6. 达到目标难度后入库。
```

难度可以定义为：

```text
L1: 静态视觉修改。
L2: HTML/CSS 多文件修改。
L3: JS 交互和 DOM 更新。
L4: 多 viewport + non-target preservation。
L5: 多轮用户需求变更。
L6: 视觉高保真 + 交互 + accessibility + 资源本地化。
```

### 5.9 Rubric / Constraint-first：先定义评价树和约束，再生成任务

参考来源：QUEST；CoVe。

WebCoding 任务可以先从评价树或约束集合开始，而不是先写自然语言需求。这样每条数据都知道自己覆盖哪些能力，也更容易验证。

建议 WebCoding rubric tree：

```text
Visual Fidelity:
  layout, spacing, typography, color, component proportions

Functionality:
  click, modal, tabs, dropdown, filtering, form validation, state update

Responsiveness:
  mobile layout, tablet layout, no horizontal overflow, nav collapse

Edit Preservation:
  target region changed, non-target region unchanged, content preserved

Accessibility:
  semantic HTML, aria labels, form labels, keyboard focus, contrast

Asset Robustness:
  local assets, no remote URL, fallback image, stable fonts

Code Quality:
  benchmark-specific format, no console error, maintainable selectors
```

CoVe 的 constraint fuzzification 可迁移为：先采样明确约束，再转成自然用户请求。

```text
显式约束:
  - pricing cards desktop 保持三列；
  - 480px 以下变单列；
  - billing toggle 更新所有价格；
  - hero/footer 不变；
  - no remote assets。

自然需求:
  “给价格区加个年付/月付切换，手机上别横向滚动，顶部和底部别动，图片和脚本都用本地的。”
```

### 5.10 Graph-grounded Task Synthesis：从页面结构图生成任务

参考来源：S1-DeepResearch。

S1-DeepResearch 用 graph-grounded task formulation 组织复杂研究任务。WebCoding 可以把页面表示成图，再从图上采样任务。

可构造的图：

```text
DOM tree:
  节点、文本、属性、层级。

Component graph:
  header -> nav -> mobile menu；product grid -> filter -> cards。

CSS dependency graph:
  selector -> affected DOM nodes；media query -> viewport behavior。

JS interaction graph:
  event source -> handler -> state -> DOM update。

User flow graph:
  click filter -> update list -> open modal -> submit form。
```

这样生成的任务会更结构化，例如从 `billing_toggle -> price_cards -> mobile_layout` 这条图路径生成“增加价格切换并保证 mobile 不溢出”的任务。

### 5.11 Trajectory Pruning：把原始长轨迹压成最小必要修复链

参考来源：WebClipper。

WebCoding agent 的原始轨迹可能包含很多无效修改、重复截图、无关文件阅读。直接训练会让模型学到低效行为。可以把轨迹构造成 action-state graph，只保留解决任务必要的信息链。

建议剪枝规则：

```text
1. 删除未影响最终代码的 patch。
2. 删除重复 render 且观察相同的步骤。
3. 删除与目标区域无关的文件阅读。
4. 合并连续小 CSS patch。
5. 保留首次暴露关键失败的测试或截图观察。
6. 重写保留步骤的 summary，让轨迹语义连续。
```

这适合把 teacher agent 的长轨迹清理成高质量 SFT 轨迹。

### 5.12 Task / Trajectory Refinement：分别修任务幻觉和轨迹噪声

参考来源：SynthAgent。

WebCoding 合成数据也会出现任务和页面不一致的问题，例如任务说“修复按钮”，但页面没有这个按钮；或者 repair 任务里 initial 实际没有 bug。SynthAgent 的 task refinement 和 trajectory refinement 可以直接迁移。

检查项：

```text
Instruction-page consistency:
  instruction 提到的 button/card/modal/form 必须在 DOM 中存在。

Bug existence:
  repair 任务的 initial 必须让测试失败。

Target reachability:
  只通过本地 HTML/CSS/JS 修改能达到目标。

Preservation feasibility:
  如果目标修改天然影响全局布局，就不要硬加“其他区域完全不变”。

Trajectory cleanliness:
  删除无效 patch、重复 render、无关探索，保留关键观察。
```

### 5.13 Exploration-grounded Task Discovery：先探索网页 affordance，再生成任务

参考来源：AutoPlay。

任务不要完全凭空生成，应先探索页面里真实存在的组件和状态。

前端探索流程：

```text
1. DOM exploration:
   提取按钮、链接、表单、输入框、卡片、section、role、label、class、id。

2. Interaction exploration:
   自动点击按钮、输入表单、打开 modal、切换 tab/dropdown/filter。

3. Responsive exploration:
   渲染 390x844、768x1024、1440x900，检测 overflow、遮挡、布局崩坏。

4. Asset exploration:
   检查图片、字体、CSS/JS 外链、console/network error。

5. Task generation:
   基于真实 affordance 生成 edit/repair/interaction task。
```

这样能减少任务幻觉，让任务和页面状态天然一致。

### 5.14 Subtask Composition：把可验证子任务组合成长程前端任务

参考来源：AgentSynth。

长程页面生成可以先造可验证子任务，再组合成复杂任务。不要直接让 LLM 生成一个超长复杂需求。

示例：

```text
Subtask 1: 创建 navbar。
Subtask 2: 创建 hero section。
Subtask 3: 添加 pricing cards。
Subtask 4: 添加 monthly/yearly toggle。
Subtask 5: 添加 FAQ accordion。
Subtask 6: 添加 mobile menu。
Subtask 7: 添加 email form validation。

Composite task:
  构建完整 SaaS pricing page，包含以上组件和交互，并保证移动端无横向滚动。
```

可以同时保留子任务轨迹和组合任务轨迹：前者训练原子能力，后者训练规划和多约束保持。

### 5.15 Trajectory-first / Goal Inference：先产生有效轨迹，再反推用户任务

参考来源：GUI-ReWalk；Trajectory2Task。

有些真实用户需求很模糊，例如“手机上怪怪的”“这个按钮不太对”“刚刚那个撤回但保留表单”。与其先生成模糊任务，不如先生成确定可执行轨迹，再反推用户表达。

流程：

```text
1. 在页面环境中产生一个有效修改轨迹。
2. 浏览器验证轨迹确实改变了目标状态。
3. 将轨迹总结成用户可见任务。
4. 加入 controlled intent adaptation：模糊、变更、撤回、不可行。
5. 用原始轨迹和最终状态做 verifier。
```

WebCoding 可覆盖：

```text
Ambiguous intent:
  “这个按钮不太对。”

Changing intent:
  “加弹窗。” -> “算了，不要弹窗，改成侧边栏。”

Infeasible intent:
  “用外部 CDN 加载字体。”但数据约束要求 local assets only。

Revert with preservation:
  “撤回刚刚颜色修改，但保留表单验证。”
```

### 5.16 World-model / Simulated Rollout：用模拟器降低真实浏览器成本

参考来源：WebSynthesis；DynaWeb。

真实 Chromium 渲染和交互验证成本较高。可以先用轻量 world model 或 DOM/render predictor 生成候选轨迹，再用真实浏览器做最终验证。

WebCoding 版本可以这样做：

```text
输入:
  当前 DOM/CSS/JS summary、截图 metadata、agent patch/action。

模拟输出:
  - 哪些 DOM 节点可能变化；
  - 哪些视觉区域可能变化；
  - 是否可能 mobile overflow；
  - 哪些 tests 可能 pass/fail。

用途:
  - 低成本筛选候选 patch；
  - 为 CSS 参数调整生成多个候选；
  - 做 visual reranking；
  - 只把高潜力样本送真实 Chromium。
```

注意：入库样本仍应以真实 Playwright/Chromium 验证为准，world model 只用于降低候选生成成本。

### 5.17 Blueprint-to-dialogue：先写任务蓝图，再生成多轮 Web edit 对话

参考来源：APIGen-MT。

多轮 WebCoding 数据容易前后不一致。可以先写结构化 blueprint，再转成自然语言对话和 agent 轨迹。

蓝图示例：

```json
{
  "initial_state": "A pricing page with three static plan cards and no billing toggle.",
  "user_goal": "Add monthly/yearly billing toggle.",
  "required_actions": [
    "add toggle UI above pricing cards",
    "store monthly and yearly prices",
    "update all displayed prices on click",
    "preserve existing card styling",
    "ensure mobile cards stack without overflow"
  ],
  "constraints": [
    "use local assets only",
    "do not change hero or footer",
    "no external JavaScript libraries"
  ],
  "verification": [
    "click yearly changes prices",
    "click monthly restores prices",
    "390px viewport has no horizontal scroll",
    "hero/footer screenshot crops remain similar"
  ]
}
```

然后由 blueprint 派生单轮 instruction、多轮用户对话、agent 轨迹和 Playwright verifier。

### 5.18 Action-graph Trajectory Synthesis：按真实前端开发动作图合成轨迹

参考来源：ASTRA。

ASTRA 用 tool-call graph topology 合成多轮工具轨迹。WebCoding 可以定义前端开发 action graph，让轨迹更像真实开发流程。

示例 action graph：

```text
inspect_file -> locate_dom_node -> locate_css_rule -> edit_css -> render_viewport -> inspect_screenshot -> run_responsive_test -> patch
inspect_file -> locate_js_handler -> edit_js -> run_interaction_test -> patch
render_desktop -> screenshot_diff -> edit_spacing -> render_mobile -> no_overflow_check
```

生成数据时先采样目标能力和 action chain，再生成任务、测试和轨迹。这样能避免随机多轮，让模型学到稳定工作流。

### 5.19 State-grounded Multi-turn Web Edit：多轮编辑必须有权威页面状态

参考来源：StateGen。

多轮 Web edit 最容易出现指代混乱，例如“刚刚那个按钮”“撤回上一步但保留表单”。需要维护 authoritative page state。

建议状态对象：

```json
{
  "dom_snapshot": "...",
  "css_rules": [],
  "js_handlers": [],
  "screenshots": {
    "desktop": "path/to/desktop.png",
    "mobile": "path/to/mobile.png"
  },
  "test_results": {
    "interaction": "passed",
    "responsive": "failed"
  },
  "confirmed_changes": ["pricing toggle added", "footer unchanged"],
  "pending_issues": ["mobile horizontal overflow remains"],
  "user_references": {
    "that button": "#billing-toggle",
    "the cards": ".pricing-card"
  }
}
```

每轮用户请求都基于这个状态生成，每轮 verifier 都检查新增约束和历史确认修改是否仍成立。

### 5.20 Procedural Component / Tool Pool：程序化生成组件、交互、bug 和验证器

参考来源：GenesisFunc；RandomWorld。

可以把 WebCoding 环境的组成元素做成可组合工具池，程序化生成大量不同前端环境。

建议工具池：

```text
Component tools:
  navbar, hero, card grid, modal, tabs, dropdown, form, table, sidebar

Style tools:
  spacing scale, typography scale, color palette, responsive breakpoints

Interaction tools:
  click toggle, filter, sort, validate, open/close, drag/drop

Bug tools:
  fixed width overflow, missing handler, wrong selector, z-index overlap, broken asset

Verifier tools:
  Playwright click, screenshot diff, DOM query, accessibility check, console check
```

程序化生成时，用组件依赖图和交互 DAG 保证任务可组合、可执行、可验证。

### 5.21 推荐落地的总 Pipeline

综合以上论文，WebCoding_Data 可以包装成：

```text
Browser-grounded Synthetic Data Engine for Frontend Coding Agents
```

或更聚焦：

```text
A Verifier-driven, Failure-adaptive Synthetic Data Pipeline for Web Coding Agents
```

建议五阶段：

```text
Stage 1: Web Environment Construction
  - real webpages
  - synthetic mini projects
  - component/template pools
  - local assets

Stage 2: Multi-source Task Synthesis
  - diff-first edit tasks
  - test/constraint-first generate tasks
  - self-play repair tasks
  - skill-oriented auxiliary tasks
  - state-grounded multi-turn tasks

Stage 3: Browser-grounded Verification
  - Chromium rendering
  - Playwright interaction tests
  - screenshot/crop comparison
  - DOM/accessibility checks
  - console/network/resource checks

Stage 4: Agent Trajectory Collection
  - inspect
  - edit
  - render
  - observe
  - test
  - patch
  - verify

Stage 5: Failure-adaptive Iteration
  - collect failures
  - classify failure modes
  - synthesize targeted data
  - retrain
  - re-evaluate
```
