# Web Coding 训练数据中的外部资源依赖调研

## 当前最新结论

1. WebCode2M 清洗主线使用 `WebCoding_Data/preprocess/webcode2m_clean_pipeline.py`。
2. 七类构造主线使用 `WebCoding_Data/construct/construct_webcode2m_dataset.py`。
3. 文本 LLM 使用 `qwen3.7-max`；视觉/PRD 使用 `qwen3-vl-235b-a22b-instruct`，图片输入使用 `image_url` content block。
4. 外部渲染依赖不进入训练样本；SVG/XML namespace 白名单保留。
5. 多页只接受真实站内 HTML 子页。
6. 最新 7x10 smoke 已通过验证：70 条、七类各 10、`remote_hit_count = 0`、`provenance_hit_count = 0`。

本文整理当前 WebRenderBench/useful 数据进一步构造 web coding 训练数据时，关于“HTML 是否可以依赖远程资源”的问题。

结论先说：

> 如果目标是训练模型生成可稳定渲染的 web 项目，关键渲染资源不应该依赖远程 URL。  
> 外部链接作为导航语义可以保留，但 CSS、JS、图片、字体等影响页面视觉的资源，应尽量本地化、内联、替换或删除。

- 内联化：把资源内容直接写进 HTML 或 CSS 里。例如把 CSS 写进 `<style>...</style>`，把很小的 SVG 或图片写成 `data:image/...;base64,...`。
- 本地化：把资源保存成项目目录里的普通文件。例如保存到 `assets/logo.png`、`assets/site.css`，再把 HTML 里的远程 URL 改成相对路径。

对训练数据来说，我更推荐“本地化”而不是无限制“内联化”。原因是图片、字体、第三方 CSS 如果全部塞进 HTML，会让样本特别长，模型会把大量上下文浪费在 base64 或压缩 CSS 上。我们真正希望模型学到的是页面结构、样式组织、资源引用关系和交互逻辑，而不是背诵一长串不可读的编码。

## 1. 背景

我们现在有一批整理后的 `31,765` 个 useful WebRenderBench 项目，路径在 H 集群：

```text
/mnt/shared-storage-user/colab-share/liujiaheng/workspace/xieqianqian/webcoding_data/h_rebuild/webrenderbench_clean_split/useful
```

这些项目目前来自原始 `train_webpages` 和 `test_webpages`，并且已经：

1. 按之前确认的 `31,765` 个 useful id 真实复制出来；
2. 对其中 `8,244` 个 AutoDL 上记录为 rescued 的项目做了原地 rescue；
3. rescue 过程中把超长 `data:image/...;base64` 或 `data:font/...;base64` 提取为本地文件；
4. 提取出的资源统一放进每个项目自己的 `assets/` 目录；
5. 不再使用隐藏目录 `.rescued_inline_assets/`。

这里的处理方式是：

1. 在 HTML/CSS/JS 文本里找到很长的 `data:image/...;base64,...` 或 `data:font/...;base64,...`。
2. 解析 MIME type，例如 `image/png`、`image/jpeg`、`font/woff2`。
3. 把逗号后面的 base64 字符串解码成二进制 bytes。
4. 根据 MIME type 选择扩展名，例如 `.png`、`.jpg`、`.webp`、`.woff2`。
5. 把二进制 bytes 写成普通文件，放到当前仓库自己的 `assets/` 目录下。
6. 把原来超长的 data URI 替换成相对路径，例如 `assets/rescued_abc123.png`。

这说明外部 URL 不全是“渲染依赖”。它们大致可以分成几类：

1. 影响渲染的关键资源：页面打开时必须加载，缺了就会明显变形或空白，例如主 CSS、首屏大图、背景图、icon font、关键交互 JS。这些资源可能放在原站服务器，也可能放在 CDN 上。
2. 影响部分视觉的图片/头像：缺了不会让整个页面崩掉，但局部会空，例如商品图、文章缩略图、用户头像、地图截图。它和第一类的区别在于影响范围：第一类影响页面整体布局和主要视觉，第二类更多影响某个卡片、列表项或局部内容。
3. 只是导航语义的超链接：例如 `<a href="https://instagram.com/...">Instagram</a>`。它只是说明“点这里会去某个页面”，不参与当前页面渲染。用户不点击时，页面显示不会依赖这个 URL。
4. SEO、RSS、pingback、dns-prefetch 等噪声：这些是给搜索引擎、浏览器预连接、博客系统或第三方服务看的元信息，通常不改变用户肉眼看到的页面。

## 3. 外部引用分类分析

### 3.1 远程 CSS

样例里有很多远程 stylesheet，例如：

```text
https://bviyachtsales.com/wp-content/cache/min/322/wp-content/plugins/login-with-phone-number/styles/login-with-phonenumber.css?ver=1755017173
https://bviyachtsales.com/wp-content/plugins/login-with-phone-number/styles/intlTelInput.min.css?ver=6.8.1
https://bviyachtsales.com/wp-content/cache/min/322/npm/tom-select@2.2.2/dist/css/tom-select.css?ver=1755017173
https://bviyachtsales.com/wp-content/themes/pro/framework/dist/css/site/stacks/integrity-light.css?ver=6.6.4
https://bviyachtsales.com/wp-content/themes/pro-child/style.css?ver=6.6.4
```

这些会直接影响页面布局、字体、颜色、组件样式。  
如果训练或渲染环境没有网络，这些 CSS 加载失败，页面视觉会偏离原本截图。

因此远程 CSS 属于高优先级清理对象。

处理策略可以是：

1. 下载 CSS 到本地 `assets/`；
2. 把 `<link rel="stylesheet" href="https://...">` 改成相对路径；
3. 如果 CSS 下载失败，先记录为 `unresolved_stylesheet`，再根据它的重要性决定删除还是保留原链接；
4. 对非常巨大的第三方 CSS，必要时做裁剪或保留本地文件但不内联。

“删除 CSS”不是直接无脑删。更合理的流程是：

1. 先看这个 CSS 的 `rel`、路径和文件名。如果是 `print.css`、`wp-block-library`、插件后台样式、评论插件样式，删除风险通常比主站 theme CSS 低。
2. 对样本做一次渲染对比：删除前后截图差异很小，才删除；差异很大，就不能删。
3. 对下载失败但看起来像主 CSS 的资源，宁可先保留远程链接并在 manifest 里标记，也不要假装已经清洗完成。

“裁剪巨大 CSS”可以有两种做法：

1. 保守做法：不裁剪，下载为 `assets/vendor_xxx.css`，HTML 改成本地路径。这最稳，但文件可能大。
2. 激进做法：用浏览器 coverage 或 CSS tree-shaking 工具，保留当前页面实际用到的选择器，删除未使用规则。这能减小体积，但有误删风险，尤其是 hover、responsive、JS 动态 class 和多页共享样式。

因此第一版 pipeline 建议先“下载到本地但不内联”，不要急着裁剪。等我们有渲染对比脚本后，再评估是否值得做 CSS 裁剪。

### 3.2 远程图片

样例里有大量：

```text
img[data-lazy-src="https://cdn.yachtbroker.org/images/highdef/...jpg"]
img[data-lazy-src="https://lh3.googleusercontent.com/..."]
```

这类图片通常不会马上出现在 `src` 里，而是懒加载字段 `data-lazy-src`。  
如果页面的 JS/lazyload 逻辑运行，它可能会把 `data-lazy-src` 复制到 `src`，从而发起远程请求。

这些图片会影响视觉完整性。例如 yacht 卡片没有图片时，页面会显得空或错位。

处理策略可以是：

1. 尝试下载到本地 `assets/`；
2. 改写 `src` 和 `data-lazy-src` 为本地路径；
3. 下载失败时用本地 placeholder 图片替代；
4. 对纯 tracking pixel 或社交头像，可以按规则删除或替换。

其他工作确实会使用 placeholder 思路。Design2Code 在构造评测时明确把 multimedia content 替换为 placeholders，并在 prompt 里要求图片用固定的 `rick.jpg`。WebSight v0.1 也不依赖真实图片，更多是 HTML/CSS 结构与截图对；v0.2 才引入真实图片。也就是说，“缺图时用本地占位图保证离线可渲染”是合理做法，但它会牺牲一部分真实视觉语义。

区分“有必要的资源图片”和“低价值图片”可以按规则做初筛，再抽样验证：

1. 尺寸规则：`1x1`、`0x0`、极小透明 gif/png 很可能是 tracking pixel。
2. URL/文件名规则：包含 `pixel`、`track`、`analytics`、`beacon`、`collect`、`counter`、`facebook.com/tr`、`google-analytics` 等关键词，多半是追踪图。
3. DOM 位置规则：在 `<noscript>` 的 analytics 代码里，或隐藏元素里，通常不是视觉必要资源。
4. 可见性规则：`display:none`、`visibility:hidden`、`opacity:0`、宽高极小的图片，训练价值低。
5. 语义规则：商品卡片、hero 区、文章封面、gallery、logo、icon 这类位置的图片优先保留。
6. 域名规则：`gravatar.com`、社交平台头像、分享按钮图标可以降低优先级，但不能一概删除，因为有些页面的作者头像或品牌头像也有视觉作用。

所以实际 pipeline 应该给每张图打标签：`critical_image`、`content_image`、`avatar_or_social`、`tracking_pixel`、`unknown`。第一版只自动删除高置信度 `tracking_pixel`，其他类别先本地化或保留记录。

### 3.3 远程 JavaScript

当前这次粗略统计没有把所有 JS 详细展开，但原始网页通常会有：

```html
<script src="https://..."></script>
```

远程 JS 对训练数据有两类风险：

1. 渲染时可能影响交互、懒加载、布局；
2. 训练时大量第三方 JS 代码通常不是我们希望模型学习的目标。

对于 web coding 训练，尤其是截图到 HTML/CSS 或页面重建任务，很多工作都会弱化或删除 JS，除非任务明确需要交互逻辑。

处理策略：

1. 先删除明显的 analytics、tracking、ads、social embed JS；
2. 对 lazyload 这类影响图片显示的逻辑，不依赖 JS，而是直接把图片路径写到 `src`；
3. 对必须保留的交互，可以本地化 JS，但需要限制体积；
4. 多页构造阶段，优先保证静态可渲染，而不是复刻完整动态站点。

这里说的 analytics/tracking/ads/social embed JS，包括 Google Analytics、Google Tag Manager、Facebook Pixel、广告竞价脚本、社交平台嵌入脚本、热力图统计脚本等。它们的作用通常是统计用户行为、加载广告、接入社交平台组件，而不是定义这个页面的核心 UI。

它们建议删除的原因是：

1. 对训练目标没有帮助：模型学会写统计脚本、广告脚本，对 web coding 页面重建能力没有明显收益。
2. 增加不可控网络请求：这些脚本会请求外部服务，让离线渲染和评测不稳定。
3. 污染代码分布：真实网页里这类脚本很多，会占用 token，让模型花容量学习无关模板。
4. 有隐私和安全风险：训练数据里保留真实 tracking endpoint 没必要。

但“删除第三方 JS”不等于删除所有 JS。我们需要包含 web coding 里的交互能力，所以应区分：

- 应删除：analytics、ads、tracking、social embed、cookie banner vendor、A/B testing。
- 可保留并本地化：菜单展开、tab 切换、轮播、弹窗、表单校验、页面内搜索、gallery 切图等真实 UI 交互。

### 3.4 外部导航链接 `a[href]`

样例里外部引用最多的是：

```text
a[href]
```

例如：

```text
https://bviyachtsales.com/yachts
https://bviyachtsales.com/yacht/2833028/...
https://www.instagram.com/bviyachtsales/
https://www.facebook.com/BVIYachtSales/
```

这类链接不一定是坏事。  
如果只是作为“页面上有一个链接”的语义，它不影响当前页面渲染。用户点击时才会跳转。

对于多页构造，有两种处理：

1. 如果这个链接对应我们生成的本地页面，就改成 `./pages/page-*.html`；
2. 如果不生成本地页面，可以保留原始 `href`，或者改成 `#` 并保留 `data-original-href`。

我倾向于：

```text
站内核心导航/卡片链接：尽量本地化为 pages/*.html
社交媒体/外部平台链接：可以保留为普通 href，或标记为 data-original-href
```

相关工作里通常不会特别强调“外部社交链接怎么保留”，因为很多 screenshot-to-code 任务会把链接行为弱化成静态 HTML。Design2Code 更关注生成页面外观与离线可运行，因此会要求不要依赖外部文件；WebSight 的样本偏合成，也不强调真实可点击外链；WebCode2M 的数据字段是渲染后的截图、HTML/CSS 文本和 layout，重点是清洗真实网页代码噪声。

对我们来说，比较实用的策略是：

1. 视觉上保留链接文本、按钮、图标，因为它们影响页面外观。
2. 站内链接如果被我们生成成多页，就改成本地 `pages/*.html`。
3. 站外链接不作为训练的渲染依赖，可以保留原始 `href`，也可以写成 `href="#" data-original-href="..."`。
4. 如果之后训练目标包含“真实网页项目结构”和“链接语义”，建议保留 `data-original-href`，这样不会丢来源信息。

### 3.5 SEO / feed / pingback / prefetch 噪声

样例里还有：

```html
<link rel="dns-prefetch" href="https://www.gstatic.com/">
<link rel="alternate" href="https://.../feed/">
<link rel="pingback" href="https://.../xmlrpc.php">
<link rel="shortlink" href="...">
```

这类内容对页面视觉几乎没有帮助，对训练 web coding 模型也价值很低。

建议直接删除。

这些词分别是什么意思：

- `dns-prefetch`：提示浏览器提前解析某个域名，加快之后访问。它不会改变页面长什么样。
- `preconnect`：提示浏览器提前和某个域名建立连接，也是性能优化元信息。
- `alternate feed` / RSS：给订阅器或搜索引擎看的文章订阅地址，不影响页面视觉。
- `pingback`：WordPress 等博客系统用于站点之间互相通知引用关系的接口。
- `shortlink`：短链接元信息，方便分享或旧系统兼容。
- `wp-json`：WordPress REST API 入口，给程序访问内容用，不是页面视觉资源。

这些东西对浏览器渲染“当前截图”通常没有必要，放进训练数据会让模型学到很多真实 CMS 的杂项模板，所以属于低价值噪声。

## 4. 相关工作怎么处理外部资源


训练或评测用的代码通常会尽量自包含，避免依赖远程资源。

### 4.1 WebSight

WebSight 是 HuggingFaceM4 发布的大规模 screenshot-to-HTML/CSS 数据集。

数据卡说明：

- WebSight 是合成网站的 HTML/CSS 代码与截图对；
- v0.1 使用 HTML + CSS；
- 数据字段里 HTML 和 CSS 直接放在同一个文本字段里；
- v0.1 不包含真实图片；
- v0.2 使用 Tailwind CSS，并包含真实图片。

这里的“包含真实图片”是指页面截图里的图片区域不只是纯色块、占位图或虚构文件名，而是使用真实图像内容来渲染页面。例如卡片里真的有照片、产品图或插画。

这对训练很重要：如果数据没有真实图片，模型容易学会布局，但对真实网页里图片与文字、卡片、视觉层级之间的关系学得不够。WebSight v0.2 引入真实图片，本质上是在缩小合成页面和真实网页之间的视觉分布差距。

它的一个关键点是：训练样本不是依赖远程 CSS，而是让模型直接看到页面实现。

对我们的启发：

```text
如果目标是让模型学会生成页面，训练样本最好是自包含或本地依赖明确。
```

### 4.2 Design2Code

Design2Code 是 Stanford/SALT lab 的真实网页 screenshot-to-code benchmark。

```text
We then remove external dependencies and replace multimedia content with placeholders.
```

并且他们会人工检查：

```text
independence from external files
```

在 prompting details 里，他们还要求模型：

```text
Do not hallucinate any dependencies to external files.
```

并规定图片用 placeholder：

```text
If it involves any images, use "rick.jpg" as the placeholder.
```

这说明 Design2Code 在评测任务里非常强调：

1. 生成代码应该能独立运行；
2. 不应该依赖外部文件；
3. 多媒体内容可以用本地 placeholder 处理。

### 4.3 WebCode2M

WebCode2M 是一个较新的真实网页大规模 code generation 数据集。

https://huggingface.co/datasets/xcodemind/webcode2m


样本字段包括：

```text
image: 截图
bbox: 页面元素布局树，包括元素类型、文本、style、bbox、children
text: HTML/CSS 代码文本
score: 质量评分
scale: 截图宽高
lang: 页面语言
tokens: CSS/HTML token 数
hash: 图像 hash
```

从 preview 看，WebCode2M 的代码已经不是完整原站工程，而是被整理成相对短的 HTML/CSS 文本；同时保留了 layout tree。这一点对我们很有参考价值：它不是只保存截图和 HTML，还显式保存了结构化布局信息，可以用于训练模型理解页面层级。

论文描述它从 Common Crawl 收集真实网页，并做：

```text
extract the associated CSS code and image elements
remove noise and irrelevant code
generate screenshots
```

WebCode2M 的 purification 可以理解为把“真实网页工程”压缩成“适合训练的页面代码”。根据论文图示和文字，它主要做这些事：

1. 从网页中抽取 HTML、CSS 和图像元素。
2. 处理 `<link>`：删除无关 link，把外链样式里的有效 CSS 转移进样本。
3. 处理 `<style>`：合并分散的样式，减少重复和碎片化。
4. 处理 inline `style` 和 `class`：保留影响布局和视觉的部分，清掉不必要的 class/id/comment/meta。
5. 删除噪声代码：例如注释、无关 meta、不可见或无意义节点、过长无关脚本。
6. 渲染 HTML 得到截图。
7. 用 neural scorer 过滤视觉质量差、加载不完整或审美较差的样本。
8. 提取 layout tree/bbox，形成 `image + text + bbox` 的训练样本。

这说明 WebCode2M 的重点不是“保真保存原网页项目”，而是“把真实网页清洗成适合模型学习的页面表示”。

对我们的启发：

```text
真实网页可以作为数据源，但不能把真实网页的全部噪声原样交给模型。
```


### 4.3.1 相关工作的 purification 步骤对比

下面按“它们大概怎么处理数据”的顺序整理。不同论文公开的细节粒度不一样，所以这里区分“论文明确写出”和“从任务设置可推断”。

#### WebSight

1. 生成或收集网页描述/主题。
2. 生成 HTML/CSS 页面代码。
3. 渲染成截图。
4. 形成 `screenshot + HTML/CSS` 训练对。
5. v0.1 更偏 HTML/CSS 和占位视觉，不强调真实图片；v0.2 引入真实图片和 Tailwind。

它的关键 purification 思路是：从源头生成相对干净、自包含的代码，而不是从真实网页里清理大量 CMS/广告/追踪噪声。

#### Design2Code

1. 收集真实网页截图和代码。
2. 删除外部依赖。
3. 把多媒体内容替换为本地 placeholder。
4. 人工检查样本是否能独立于外部文件运行。
5. 在评测 prompt 中要求模型不要编造外部依赖，图片统一用 placeholder。

它的关键 purification 思路是：评测样本要离线、自包含、可复现，不能让远程资源影响评价。

#### WebCode2M

1. 从 Common Crawl / 真实网页资源中收集网页。
2. 抽取 HTML、CSS、图片元素。
3. 对 `<link>` 做删除和样式转移。
4. 对 `<style>` 做合并。
5. 清理 style/class/comment/meta 等噪声。
6. 渲染页面得到截图。
7. 用质量评分模型过滤低质量或不完整页面。
8. 提取 layout tree/bbox。
9. 输出 `image + HTML/CSS text + bbox + score + lang + tokens`。

它的关键 purification 思路是：保留真实网页的多样性，但把真实工程噪声变成干净、统一、可训练的页面表示。

#### Web2Code

1. 整理已有 webpage-to-code 数据。
2. 构造网页截图到 HTML code 的 instruction tuning 样本。
3. 用网页理解和代码生成任务一起提升 MLLM。
4. 通过渲染/评测框架评价模型输出。

公开摘要没有细到每个资源清洗规则，但它的任务目标要求模型输出可渲染 HTML，因此不适合依赖不可控远程 CDN。

#### FullFront

1. 从真实网页出发。
2. 用两阶段流程把真实网页转换成 clean, standardized HTML。
3. 避免直接使用 bloated scraped code。
4. 构造更接近前端工作流的 benchmark。

它的关键 purification 思路是：真实网页有价值，但原始代码太臃肿，必须标准化后才适合训练/评测。

#### WebRenderBench

1. 从真实网页/MHTML 出发。
2. 转成标准 HTML 和静态资源。
3. 用本地 web server 渲染目标页面和生成页面。
4. 评估生成结果与目标截图的视觉相似度。

它的关键 purification 思路是：目标页面应该尽可能在本地 server 下渲染。但我们当前样例说明，原始数据仍残留一部分远程链接、lazy image、metadata 和外部 CSS，所以还需要二次清洗。

### 4.4 Web2Code

Web2Code 是 NeurIPS 2024 的网页到代码数据集和评估框架。

其抽象是：

```text
inputs: webpage images + instructions
responses: webpage HTML code
```

它强调用已有 webpage-to-code 数据集增强，并生成新的网页，再渲染成图片。

虽然 arXiv 摘要没有细到每个资源处理规则，但从任务形式看，它追求的是：

```text
给定截图/指令，模型输出 HTML code
```

这种任务天然要求输出代码在评测环境中可渲染。  
如果输出依赖随机远程 CDN，就会让评测不可控。

来源：

```text
https://arxiv.org/abs/2406.20098
```

### 4.5 FullFront

FullFront 是 2025 年的 front-end workflow benchmark。

摘要里提到：

```text
Unlike existing benchmarks that use either scraped websites with bloated code or oversimplified LLM-generated HTML,
FullFront employs a novel, two-stage process to transform real-world webpages into clean, standardized HTML
```

这和我们的情况很像：我们也是从真实网页来，但原始网页有大量噪声。

对我们的启发：

```text
真实网页的视觉多样性有价值，但需要转成 clean, standardized HTML。
```

来源：

```text
https://arxiv.org/abs/2505.17399
```

### 4.6 WebRenderBench 本身

WebRenderBench 的说明里提到：

```text
Each pair consists of a real webpage (HTML + resources) and its rendered screenshot.
The script launches a web server to render both generated and target HTML.
```

第三方介绍中也提到类似：

```text
MHTML files are converted to standard HTML with static resources;
non-local media elements are replaced by local counterparts
```

也就是说 WebRenderBench 原始目标也是让网页在本地 web server 下可渲染。

但我们现在看到的样例里仍然存在远程引用，说明：

1. 原始数据已经本地化了一部分资源；
2. 但不是所有远程引用都被完全去除；
3. 一些 `data-lazy-src`、远程 stylesheet、SEO 链接仍然留在 HTML 里。

来源：

```text
https://huggingface.co/datasets/aleversn/WebRenderBench
```

## 5. 外部资源对模型训练的影响

### 5.1 负面影响一：训练目标不稳定

如果页面渲染依赖远程资源，那么同一个 HTML 在不同时间、不同机器、不同网络环境下可能显示不同结果。

例如：

```text
今天 CDN 可访问：图片正常
明天 CDN 失效：图片空白
训练机器无外网：CSS/图片全挂
```

这会导致：

```text
同一份代码 -> 不同视觉结果
```

对于 screenshot-to-code 或 web coding 数据，这是很糟糕的。

### 5.2 负面影响二：模型学习无意义 URL

如果训练数据里有大量：

```html
<link href="https://some-site.com/wp-content/cache/..." rel="stylesheet">
<img data-lazy-src="https://cdn.xxx.com/images/abc.jpg">
```

模型可能会学到：

1. 生成大量真实网站 URL；
2. 依赖外部 CDN；
3. 把实现细节推给远程资源。

但我们希望模型学会的是：

```text
如何组织 HTML/CSS/JS/本地 assets 来实现页面
```

而不是记住一些无用的远程资源链接。

### 5.3 负面影响三：代码噪声变大

真实 WordPress / Shopify / Webflow 页面常包含很多：

```text
plugin CSS
tracking JS
analytics JS
dns-prefetch
RSS feed
pingback
shortlink
schema metadata
```

这些对前端视觉构造的训练价值很低，却会占用上下文长度。

它们对 web coding 训练价值低，主要因为它们不教模型“如何把页面做出来”：

1. `plugin CSS` 往往是某个 CMS 插件的通用样式，里面大量规则当前页面根本没用。模型学到的是插件模板，而不是页面布局能力。
2. `tracking JS` 和 `analytics JS` 的目标是统计访问行为，不负责页面主要视觉。学会写这些代码不会提升截图还原、布局构造或交互实现。
3. `dns-prefetch`、`RSS feed`、`pingback`、`shortlink` 是系统元信息，用户肉眼看不到，对页面结构和样式几乎没有贡献。
4. `schema metadata` 主要给搜索引擎理解内容，不参与视觉渲染。
5. 它们会占用 token。训练时模型上下文有限，这些低价值代码越多，HTML 结构、CSS 规则和真实交互代码的学习空间越少。
6. 它们会引入错误归因。模型可能以为一个页面需要大量外部脚本和 CMS 元标签才能成立，反而弱化了直接写干净 HTML/CSS/JS 的能力。

Design2Code 和 WebCode2M 都提到真实网页代码很长、很噪。WebCode2M 甚至专门做 code purification。

### 5.4 负面影响四：评测不可复现

如果未来我们用浏览器渲染模型输出，并和目标截图比：

```text
远程资源加载成功与否
```

会直接影响评价指标。

这会把模型能力评估和网络状态混在一起，不利于判断模型真的学到了什么。

## 6. 什么外部东西可以保留，什么应该清理

我建议区分处理：

### 6.1 可以保留的

#### 普通跳转链接

例如：

```html
<a href="https://www.instagram.com/...">Instagram</a>
<a href="https://original-site.com/contact">Contact</a>
```

如果它只是一个链接，不影响当前页面渲染，可以保留。

但更稳的方式是：

```html
<a href="#" data-original-href="https://...">Instagram</a>
```

或者在多页构造时，如果我们生成了对应本地页面，就改成：

```html
<a href="./pages/page-1.html">...</a>
```

#### 原始 URL metadata

可以用 `data-original-href`、manifest 或注释保存原始 URL，方便追踪来源。

意思是：即使我们为了离线训练把链接改成本地路径或 `#`，也不要完全丢掉原始 URL。比如原来是：

```html
<a href="https://bviyachtsales.com/yacht/2833028/...">View details</a>
```

多页构造后可以改成：

```html
<a href="./pages/page-1.html" data-original-href="https://bviyachtsales.com/yacht/2833028/...">View details</a>
```

这样浏览器点击会去本地页面，训练和渲染不依赖外网；但我们仍然知道这个页面原来对应哪个真实 URL。以后如果要 debug、溯源、重新抓取、构造更真实的多页关系，这个字段会很有用。

### 6.2 应该本地化的

这些影响视觉，应该优先处理：

```text
link[rel=stylesheet][href^=http]
img[src^=http]
img[data-lazy-src^=http]
source[src^=http]
video poster/src
font-face url(http...)
CSS background-image: url(http...)
```

处理方式：

```text
下载到 assets/
改成相对路径
下载失败则替换 placeholder
```

### 6.3 应该删除的

这些一般不该进入训练数据：

```text
dns-prefetch
preconnect
pingback
alternate RSS/feed
shortlink
wp-json API link
analytics script
tracking pixel
ads script
social embed script
```

### 6.4 需要谨慎处理的

#### JavaScript

如果任务目标只是静态页面复刻，远程 JS 大多应该删除。  
但我们的目标不是纯静态页面，而是 web coding 训练数据雏形，所以应该保留“真实 UI 交互”。

如果任务目标包含交互，则应：

1. 下载到本地；
2. 限制体积；
3. 去掉 analytics/tracking；
4. 明确记录该项目依赖 JS。

更准确的规则应该是：

```text
保留并本地化：菜单、tab、accordion、carousel、modal、dropdown、form validation、搜索、筛选、分页、gallery 等交互。
删除或替换：analytics、ads、tracking、social embed、A/B testing、cookie consent vendor、远程地图/支付/聊天客服等第三方业务脚本。
```

也就是说，我们不是不要 JS，而是不要让训练数据被第三方商业脚本淹没。最终训练集应该包含适量、可读、和页面交互直接相关的 JS。

#### 字体

远程字体会影响视觉，但下载字体可能增加体积。  
可以折中：

1. 优先保留系统字体 fallback；
2. 对关键 webfont 下载本地；
3. 大规模批处理时，先统计字体依赖比例再决定。

相关工作里，字体通常不是单独作为“训练目标”讨论，而是作为样式/渲染一致性的一部分处理：

- WebSight 强调 CSS 直接嵌入 HTML；如果使用 Tailwind 或系统字体，字体问题被弱化。
- Design2Code 要求不要依赖外部文件；这意味着远程字体如果影响页面，就不应该作为外部依赖存在。评测更关注整体视觉还原，而不是要求模型复刻某个商业 webfont。
- WebCode2M 更关注 HTML/CSS purification 和截图质量，没有把字体作为独立贡献点；从 preview 看，样本代码里会出现 `font-family`，但不一定保留完整远程 font 文件。
- FullFront 强调 clean, standardized HTML，也说明它更倾向于清理真实网页工程噪声，而不是保留所有第三方字体依赖。

我的建议是：字体要进入渲染处理，但不要作为模型重点学习对象。

具体策略：

1. CSS 里的 `font-family` 可以保留，因为它表达设计风格。
2. 远程 Google Fonts / Adobe Fonts / icon font 如果能稳定下载，保存到 `assets/` 并改成本地路径。
3. 下载失败时使用系统 fallback，例如 `Arial`、`Inter`、`system-ui`、`sans-serif`。
4. 对 icon font 要更谨慎，因为它可能影响图标显示。如果页面大量用 icon font，最好本地化；否则图标会变成方块。
5. 不建议把大型字体 base64 内联到 HTML。字体文件放在 `assets/` 更合理。

## 7. 对当前数据集的建议方案

我建议把处理分成四个阶段，而不是一次性做很重的批量改造。

### 阶段 A：外部资源审计

对 `31,765` 个项目扫描：

```text
每个项目有多少 external stylesheet
多少 external script
多少 external image/src/data-lazy-src
多少 external font/background url
多少 external a href
```

输出 manifest：

```text
external_resources_report.jsonl
external_resources_summary.json
```

这一步只读，不改数据。

目的：

```text
先知道问题规模，再决定清洗优先级。
```

### 阶段 B：删除低价值噪声

先处理安全、确定、不会影响主要视觉的东西：

```text
dns-prefetch
preconnect
pingback
alternate feed
shortlink
wp-json API link
analytics/tracking scripts
```

这一步风险低，收益是减少噪声。

### 阶段 C：本地化关键渲染资源

优先处理：

```text
CSS
图片
字体
background-image
lazy image
```

建议统一下载到：

```text
assets/external/
```

或者如果你希望简单，也可以直接放到：

```text
assets/
```

命名方式建议用 hash 防冲突：

```text
assets/sha1.ext
```

HTML/CSS 中改为相对路径。

下载失败时：

```text
图片 -> placeholder
CSS -> 删除或记录 unresolved
字体 -> fallback
```

### 阶段 D：多页构造

在资源尽量本地化之后，再做多页构造更稳。

多页规则建议：

```text
优先选择站内 a[href] 链接
每个项目生成 3-5 个 page
生成的 page 共享 assets/
首页改成本地链接
保留 data-original-href
```

这样训练模型能学到：

```text
多文件项目结构
相对路径
页面间导航
共享 assets
```

而不是学到：

```text
把所有东西链接到外网
```

## 9. 推荐的最终原则

我建议我们对 web coding 训练数据采用下面的原则：

### 原则 1：训练样本必须离线可渲染

不要求完全没有外链，但关键视觉资源必须本地可用。

### 原则 2：普通外部 a href 可以保留，但不要作为关键页面依赖

外部链接可以作为语义存在；如果它是我们构造的页面关系，就改成本地 `pages/*.html`。

### 原则 3：CSS / 图片 / 字体优先本地化

这些直接影响视觉，是训练和评测的一致性核心。

### 原则 4：第三方 tracking / analytics / feed / pingback 等噪声删除

它们对 web coding 训练价值低，会污染模型。

### 原则 5：不要让模型学习超长 base64

我们已经做了 rescue，把 inline image/font data URI 提取到 `assets/`，这个方向是对的。

### 原则 6：不要一开始批量大改

先抽样 100 个项目做审计和本地化，渲染检查通过后再全量。
