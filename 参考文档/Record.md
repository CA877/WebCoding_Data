- 编辑任务
往网页里临时注入一段 JavaScript，让页面上出现一些“彩色框标注”
比如主页原来长这样：
顶部导航栏：
Home | Products | About | Contact
注入 overlay 后，截图里可能变成：
Home | [红框 Products] | [蓝框 About] | [绿框 Contact]
红框表示：
这个区域是一个链接，点击它会跳到 products 页面。
蓝框表示：
这个区域是一个链接，点击它会跳到 about 页面。
它不是修改原始网页内容，而是在截图时额外叠了一层视觉提示。论文原话是，他们解析 index.html 中引用的子页面 URL，随机选两个子页面截图，并在主页截图中注入 JavaScript overlay，用彩色 bounding boxes 高亮子页面链接位置，以测试模型是否能复现多页面网站及页面依赖关系。
**这对 Vision-Guided Generation 很重要，因为模型只看截图时，不一定能理解页面之间的跳转关系。**

- 单页sp and 多页mp
“共享资源”一般指这些东西：
1. 公共 CSS / theme 文件
2. 公共组件，比如 Navbar、Sidebar、Button、Card
3. 公共图片、图标、字体
4. 公共状态管理逻辑
5. 公共路由配置
6. 公共数据 mock 文件

例如：
单页版本：
只有一个商品展示页。

多页版本：
首页
商品列表页
商品详情页
购物车页
用户中心页

共享资源：
顶部导航栏
商品卡片组件
购物车状态
全局主题样式
商品 mock 数据

这样做的目的，是让 editing 任务不只是“改一个孤立页面”，而是测试模型能不能在一个更真实的项目结构里修改代码。
比如编辑指令是：给商品卡片加一个收藏按钮，并在商品详情页也保持同样风格。
这时模型就必须理解多个页面之间的组件复用关系，而不是只改一个 HTML 文件。

- vision-guided edit：
论文对 Vision-Guided Editing 的定义是：输入包括当前网页截图、对应代码仓库和编辑指令，模型输出 patch，让编辑后的网页满足指令。
1. 第一种：输入：
当前页面截图 + 修改指令

指令：
把页面右侧的统计卡片改成两列布局，并增加 hover 效果。
2. 第二种：输入：
当前页面截图 + 目标效果截图 + 代码仓库

输出：
patch

- repair任务
  bug不止一个
  给出模糊提示，但不泄露实现细节
  每个 repair instance 还有精确的 search/replace 标注，保证唯一、可运行、可验证的解。
  限定任务边界：
你应该修复哪类问题？
问题大概发生在哪里？
修复目标是什么？
例如：当前页面存在布局问题，商品卡片中的文字和按钮发生重叠，请修复。

没有告诉模型：
改哪个 class
改哪个 css
margin 改成多少

如果完全不提供文字描述，任务会变成：
代码审计 + UI审美判断 + bug localization + bug fixing
输出code patch

三类问题：
1. 视觉布局问题
   遮挡、拥挤、文本重叠、对齐错误、对比度不足、溢出、尺寸比例失真

2. 语义与结构问题
   语义结构错误、嵌套结构错误、属性缺失

3. 交互可用性问题
   交互断掉、按钮不能点、功能失效

   主要不是“项目完全跑不起来”的编译错误修复，
而是“网页能打开，但视觉、结构、交互上存在可观察缺陷”的前端修复任务。
