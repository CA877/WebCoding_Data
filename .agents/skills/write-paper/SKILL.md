# WebCoding 论文演化叙事

当用户撰写、修改、梳理或评审 WebCoding 的研究方案、论文方法、引言、图表或口头呈现时，使用本 skill。目标是把研究呈现为一条因果主线，而非若干并列的增广技巧。

## 核心主张

在保留工程与能力承接关系的条件下，借助真实网页中可观察的前端功能灵感，改变 seed 网页的主任务；新任务依次推动用户操作、交互组织和界面结构变化。将该变化实例化为一串具有视觉与行为证据的功能级 Edit，得到视觉和交互任务明显不同、但与原项目存在技术继承关系的新前端项目。

因果链必须明确写为：

`主任务改变 → 用户操作改变 → 交互方式重组 → 界面结构改变 → 新的产品身份`

不要把角色/产品身份变化、交互范式替换和 layout 重构写成彼此独立、随机组合的策略。产品身份是因果链的结果；视觉或交互大幅变化必须由新的任务和操作流程解释。

## 写作与方案约束

- 新主任务是具体的用户操作流程，不是一句产品名称。它至少说明用户在哪个界面区域做什么、信息如何出现、哪些状态改变、哪些组件联动。
- 工程承接不等于保留组件树或旧 layout。可复用数据对象、展示能力、状态逻辑和工程配置；呈现、入口、组件组合及操作组织可以重构。
- 功能灵感库保存完整的前端行为案例：用户动作、界面证据、状态变化及实现参考。迁移的是行为关系与实现启发，不是 donor 的外观、代码片段或假定存在的历史 diff。
- 灵感库贯穿两次决策：先帮助判断 seed 可演化出的新工作界面，再依据每一个当前页面状态选择最能推进目标流程的下一项功能。
- 大目标在一条轨迹内保持稳定；根据浏览器执行结果调整后续功能和顺序，但不能让路径任意漂移成无关产品。
- 一个 Edit 的“局部”由语义边界界定，不由 diff 行数界定。所有修改都应服务于该功能；布局替换、默认视图变更等必要变化必须写入指令，不能藏在无关 diff 中。
- 每个接受状态要保存真实浏览器得到的视觉和交互证据。验证操作后的状态与跨组件同步，也检查原有应保留的能力；初始截图、补丁回放或模型声明均不足以单独证明功能成立。
- 若主张多模态训练，样本本身必须保留视觉输入；合成阶段使用视觉模型不自动使训练样本成为多模态。
- 生成、编辑、修复数据可来自同一演化轨迹：功能级状态变化形成 Edit，核对过的当前完整需求/视觉参考对应 Generate，真实执行中的已修复问题形成 Repair。不要把三者描述为无关的平行造数管线。

## 论文表述边界

将数据质量、训练收益或能力提升明确表述为待验证研究假设，除非已有对应实验结果。避免声称“最大化感知距离、最小化底层能力距离”；采用更准确的目标：

> 以工程与能力承接为约束，扩大有效的界面及交互任务差异。

方法中的角色分工应清楚：主任务变化提供变化理由；功能灵感库提供可迁移的前端能力；序列推荐组织路径；界面与交互重组是路径结果；diff 与真实运行证据将结果转为训练数据。
