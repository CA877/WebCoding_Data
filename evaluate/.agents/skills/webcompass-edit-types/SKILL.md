# WebCompass 16 类 Edit 操作

## 职责与边界

本 skill 是 WebCompass Edit taxonomy 的专门知识与审核入口。它处理：

- 用通俗语言解释 4 个大组、16 个官方操作类型；
- 按核心行为而不是关键词给现有 Edit 指令分类；
- 判断一项需求是完整的官方类型任务，还是按钮、样式、反馈等局部子行为；
- 为不同类型选择 DOM/ARIA、真实动作、时间采样、几何或图像证据；
- 说明单页、多页、模拟前端状态和真实后端能力之间的边界。

工作流路由：

- 只生成连续 Edit 指令时使用 `generate-edit-instructions`；
- 构造 target、patch 或正式数据时使用 `synthesize-data`；
- 实现网页、运行浏览器验收或生产自然 Repair 时使用 `run-webcoding-harness`；
- 本 skill 可以和上述 skill 同时使用，但不会自行启动生成、浏览器或数据发布。

## 必须遵守的分类口径

1. 官方类别只有 16 个。历史目录、自定义标签或普通 UI 小功能不得称为新的“WebCompass 官方类型”。
2. 根据用户要求的核心对象、操作、状态变化和可见结果分类，不能根据出现了 `table`、`upload`、`login` 等词就直接贴标签。
3. 一项完整任务可以同时命中多个类别；需要时给出主类别、次类别及各自依据，不强迫单标签。
4. 小型 loading spinner 不自动等于 Skeleton Loading；一个可编辑文本框不自动等于 Rich Text Editor；登录弹窗外观不自动等于 User Authentication。
5. 一条 WebCompass Edit 记录可以包含多个子任务。子任务数、操作类型数、patch 块数和修改文件数是四个不同概念。
6. `mp` 描述输入项目含多个独立页面，不代表指令必须修改每一页。没有 target、patch 或 affected-page 证据时，不推断跨页覆盖范围。
7. 公开官方 Edit 样本中的描述可以证明“要求做什么”，不能在缺少 target/patch 时证明“标准答案如何实现”或“实际修改了哪些文件”。
8. 前端模拟登录、上传、实时更新只能证明相应的前端状态流程；不能据此声称真实认证安全、服务端持久化、网络上传或实时服务已经成立。

## 使用详细参考

遇到以下任一任务时，完整读取 [references/operation-types.md](references/operation-types.md)：

- 逐类解释或比较 16 类；
- 为某一类举官方数据实例；
- 分类或审核一批 Edit 指令；
- 设计每类的浏览器验收；
- 判断两个相近类型的边界。

该参考包含官方四组分类、每类核心语义、真实公开数据实例、最低完整度、状态变化、验收证据和常见假通过。

## 回答或审核格式

### 解释某一类型

至少说明：

1. 它解决什么交互问题；
2. 构成该类型的核心行为；
3. 一个官方数据实例或明确标注的自造例子；
4. `修改前 → 用户动作/时间 → 修改后` 的状态变化；
5. 应怎样在浏览器中验收；
6. 哪些表面实现不能算完整通过。

### 给现有指令分类

输出：

| 指令 | 主类型 | 次类型 | 核心依据 | 缺失或不确定项 |
| --- | --- | --- | --- | --- |

分类理由必须引用实际行为和状态，不以类别名称复述指令。若任务粒度不足，写“接近某类型，但未达到完整任务”，并指出缺少的关键状态。

### 审核覆盖或完整度

逐项检查：

- 是否有明确业务对象和操作入口；
- 是否定义关键状态及状态之间的转移；
- 是否说明成功、失败、空态、结束态或恢复态中真正必要的部分；
- 是否与现有网页内容和数据相容；
- 是否包含可执行的验收结果；
- 是否把装饰性反馈误当成完整能力；
- 多页任务是否明确作用页面或共享模块，而非笼统要求覆盖全部页面。

最终分别报告“类别覆盖”“任务完整度”“可验收性”；不要把三者合并成一个笼统的通过结论。
